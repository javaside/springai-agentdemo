# 子 agent 实现原理

> 本页讲**实现**：子 agent 是什么、三种执行模式怎么跑、结果怎么回到模型、取消怎么落地。
> 面向使用者的说明在 README「子 agent」章节与 [background-agent.md](background-agent.md)；
> 实现索引见 [implementation-map.md §12-13](../implementation-map.md)。

---

## 1. 一句话：子 agent 是什么

**子 agent = 一个临时 ChatClient + 一次独立的模型调用。**

它不是常驻进程，也没有自己的消息循环。被派出去时创建、跑完即销毁。核心特征有三条：

| 特征 | 含义 |
| --- | --- |
| **上下文独立** | 不挂会话记忆 advisor，看不到主对话历史。所以派发 prompt 必须自包含（工具描述反复强调 "self-contained"） |
| **结果只回最终文本** | 子 agent 内部几十轮工具调用都不进主会话，回给主 agent 的只有最后一条消息——这就是委派能省主 agent 上下文的机制 |
| **工具/模型继承自主 agent** | 拿到的是主 agent 那套**已装饰**工具（权限审批、工具事件、媒体外置全套生效），可按定义裁剪；模型默认跟随当前所选 |

## 2. 参与的类（一张图）

```
定义层    agents/*.md ──→ SubagentLoader ──→ SubagentSpec（name/描述/系统提示/allow/deny/model）
                                                    │
工具层    SubagentTool ── "Task"（单个）            │
         SubagentTool ── "ParallelTasks"（批量）    │  路由：subagent_type → spec
         BackgroundTaskTool ── "TaskOutput"（取结果，仅主 agent）
         BackgroundTaskListTool ── "ListTasks"（列清单，仅主 agent）
                                                    │
执行层    SubagentRunner.run / runAll / runInBackground ──→ execute()（共用执行体）
                                                    │
后台层    BackgroundTaskRegistry（状态真相源）· TaskResultStore（限幅落盘）
         BackgroundNotifier（自动送达判定+刹车）· BackgroundDigest（给模型的统一措辞）
```

装配点在 `AgentTools.build`：`SubagentRunner` 复用主 agent 的已装饰工具列表；
`TaskOutput` / `ListTasks` / 记忆工具 / `ExitPlanMode` **刻意不进**这份列表——
子 agent 没有自己的后台任务，也不该替用户写记忆、交计划。

## 3. 定义：agents/*.md

四个内置定义放在 classpath `/agents/` 下，frontmatter + 正文：

```
---
name: explore
description: Read-only codebase exploration specialist...   ← 进 Task 工具描述里的清单
tools: Read, Grep, Glob                                      ← allowTools 白名单
---
You are a codebase exploration specialist...                ← systemPrompt 正文
```

- `tools` 为空 = 继承全部工具；`disallowedTools` 在 allow 结果上再剔除。
- `model` 可空；非空时**只在当前 provider 上**按模型名覆盖（跨家路由未实现）。
- 内置四件：`general-purpose`（几乎全工具）、`explore`/`plan`（只读三件套）、
  `bash`（Bash 系列）。
- 不支持用户自定义子 agent（没有扫描 `.codetui/agents/` 的代码）。

子 agent 的系统提示**每次派发现拼**：spec 正文 + AGENTS.md 项目指令 +
权限模式段（实时读当前模式，Shift+Tab 切档下一次委派即生效）+ 产物路径提示
（提醒它把生成的图片路径写进最终报告，否则主 agent 不知道那些图存在）。

## 4. 三种执行模式

同一个执行体（`execute()`：建临时 ChatClient → 一次阻塞调用跑完整个工具循环），
三种交付模式：

### 4.1 前台单个（Task，默认）

```
主 agent 工具线程 ──调用 Task──→ 阻塞执行子 agent ──→ 返回最终文本
                                                     （文本即工具结果，回合继续）
```

工具线程同步等。适合「下一步就依赖这个结果」的串行流程。

### 4.2 前台并行（ParallelTasks）

**并发执行、同步汇合**（fork-join）：

```
主 agent 工具线程
 ├─ 建回合级临时线程池（同时最多 4 路，可配）
 ├─ N 个子 agent 各占一线程同时跑   ← 任务之间是真并发
 └─ invokeAll 阻塞等全部完成 ──→ 按入参顺序逐条返回
                                  单条失败 → 该位置返回「失败：<原因>」，不影响其他条
```

对调用方是同步的，但子任务彼此并发——3 个 60 秒的任务约 60 秒完成，而非 180 秒。
未知 subagent_type 在批量模式下**降级为失败文本而不抛异常**（失败隔离），
这与单任务模式（抛异常）有意不同。

### 4.3 后台（run_in_background=true）

```
主 agent 工具线程 ──→ 立即返回「已在后台启动：task_xx」   ← 工具调用到此结束
                          │
常驻线程池 ──────────────┘ 子 agent 慢慢跑，跨回合存活
```

- **立即返回**，主回合立刻恢复；返回文本里带 taskId，它是模型日后取结果的凭据。
- **不进 busy 闸门**：后台任务在跑不挡用户发新消息（这是后台化的核心收益）。
- **跨回合存活**：Esc 取消当前回合不影响它；只有 `/tasks` 面板 k 键、`/clear`、
  退出能终止。
- **权限审批一律拒绝**：主回合可能早结束了，弹审批面板没人应答——所以引擎判出
  「需要询问」时后台直接 DENY。因此后台任务应只派只读或预授权的活（工具描述
  里把这条准则写给了模型）。
- 注册表容量 64，满了淘汰**最旧的已结束**任务（运行中永不淘汰）；不落盘、不跨进程。

三种模式对照：

| | 前台单个 | 前台并行 | 后台 |
| --- | --- | --- | --- |
| 对工具线程 | 阻塞到完成 | 阻塞到全部完成 | 立即返回 |
| 子任务间 | — | 并发（≤4 路） | — |
| 生命周期 | 绑定回合 | 绑定回合 | 跨回合 |
| Esc 取消 | 出站净化兜底 | 拆线程池 | 不受影响 |
| 进 busy 闸门 | 是 | 是 | **否** |

## 5. 模型怎么「发现」后台任务

模型看不到注册表，它只看得到**进入会话的文本**。五条通道，措辞统一出自
`BackgroundDigest`（保证模型从任何一路看到的说法一致）：

| 通道 | 时机 | 内容 |
| --- | --- | --- |
| 发起返回值 | 派发那一刻 | 「已在后台启动：task_xx」——taskId 的第一现场，落在会话历史里 |
| `ListTasks` | 模型随时可调 | 全部任务清单（id/agent/描述/状态）。救 `/compact` 压掉历史 id 的场景 |
| `TaskOutput` | 模型需要时 | 取单个结果（见下节） |
| 自动送达 | 系统空闲时 | UI 起新回合把结果作为 user 消息送进会话 |
| `/continue` 注入 | 用户敲 /continue | 「运行中→别重复委派；已完成待取回→先 TaskOutput」 |

## 6. 后台结果的回收：两条路互斥

同一个结果**绝不送两遍**——注册表的 `markConsumed` 返回值做互斥闸，
谁先取到 true 谁负责送，另一方拿到 false 就跳过。

### 6.1 TaskOutput：回合内出口

**它解决的唯一问题：回合还活着、模型的下一步就需要这个结果。**
此刻自动送达被 busy 闸拦着（回合进行中永不送），TaskOutput 是唯一出口。
模型一次不调也完全正常——自动送达兜底，两条路互斥不撞车。

四种返回（`block=false` 时是纯查询，`block=true` 时最多等 300 秒）：

| 任务状态 | 返回给模型 |
| --- | --- |
| RUNNING | 「仍在运行，稍后再取」（**超时也返回这句，不是失败**——把「没跑完」说成失败，模型会去重派一个一模一样的任务） |
| DONE | 限幅后的结果正文，标记已消费 |
| FAILED | 摊平后的失败原因，标记已消费 |
| KILLED / 查无此 id | 终止说明 / 三种解释 + 当前全量清单 |

`block=true` 的等待有**让路设计**：等待发生在主 agent 工具线程上，期间主 agent
不发模型调用，而模型调用恰是用户插话的唯一送达点。所以轮询每 200ms 顺路看一眼
插话队列，有就提前返回「仍在运行」——否则「后台」会被 block=true 抵消成前台。

### 6.2 自动送达：空闲时的兜底

模型可能派完就结束回合、甚至忘了这回事。系统的兜底（跑在 TUI 的 UI 更新批里，
事件驱动、空闲时零周期任务）：

```
每个空闲 UI 批检查（按序）：
  ① 主回合空闲？（无回合、无模态、无在飞前台子 agent）
  ② 输入框为空？（用户正在打字时不抢跑）
  ③ 刹车未踩？（连续自动送达 < 3 次）
  全过 → 合并全部待送达结果为一条通知 → 起新回合（同会话内，结果作为 user 消息进历史）
```

**失控刹车**：自动起的回合里模型可能又派后台任务 → 完成又自动起回合 → 无人值守时
无限烧钱。故连续自动送达 3 次即停，状态栏提示「回车交给模型」；任何真实用户提交
归零计数。**提交失败不标记已消费**——标记就等于把结果丢了，下一拍重试。

### 6.3 两条路的分工一句话

> **自动送达 = 系统对模型的默认假设**（它可能是被动的、健忘的）；
> **TaskOutput = 给「回合还活着且恰好需要」留的出口**。

## 7. 结果限幅

后台结果进入会话的**唯一入口**做了限幅（默认 4000 字符）：超限时完整正文落盘到
`.codetui/artifacts/task-<id>.txt`，进会话的是前 4000 字 + 文件路径。
落盘失败降级纯截断并如实说明——给一个取不回的路径比不给更糟。

## 8. 取消语义（前台）

Esc 取消回合时，对并行子 agent 是**拆线程池**：每个回合的临时池都登记在
`poolsByTurn`，取消时逐池 `shutdownNow`、**立即返回不等收尾**——保证 UI 快速回到
空闲。阻塞在网络 IO 的线程可能不响应中断继续跑完，这是已知取舍，由三道兜底接住：

1. 迟到的 UI 事件被 turnId 过滤器丢弃；
2. 下一回合出站前净化会话（裁掉悬空 tool_calls，防下条请求 400）；
3. 在飞计数喂 busy 闸门——旧子 agent 没清完之前，新消息排队而不是立即起跑
   （杜绝两回合并发写同一会话）。

后台任务与取消无关（见 §4.3）。三个终止入口语义严格分开：

| 入口 | 语义 |
| --- | --- |
| `/tasks` 面板 k 键 | 终止单个运行中任务（先确认） |
| `/clear` | 终止全部 + **换一个新池**（进程还要继续用） |
| `/exit` / Ctrl+C | 终止全部 + **永久关池**（有界 2s 收尾，不卡退出） |

## 9. UI 可见性

- **前台子 agent** → 「⤷ 任务面板」：▶/✓/✗ + 当前在跑的工具；内部工具活动带
  taskId 实时上报、缩进渲染。事件带 turnId，回合取消后的迟到事件被过滤。
- **后台子 agent** → 「⏱ 面板」：跨回合累积，/clear 才清；起止各一行进滚动区，
  过程与结果正文不进（不打断主对话）；`/tasks` 面板可展开结果正文（界面唯一
  看到全文的地方）。事件**刻意不带 turnId**——后台任务跨回合存活，带了会被
  迟到过滤器误杀。

## 10. 设计要点速记

1. **状态、判断、执行分离**：注册表只管状态机，自动送达判定是纯状态机
  （BackgroundNotifier），执行在 UI——三者各自可单测。
2. **前台/后台共用执行体**：模型、工具集、系统提示、重试策略同源，防止
  「后台任务行为和前台不一样」这类最难排查的漂移。
3. **在飞计数分两个**：前台计数喂 busy 闸门；后台计数刻意**不**喂——混在一起
   「后台任务在跑就挡新回合」= 后台化白做。
4. **给模型的措辞单一出处**（BackgroundDigest）：五条可见通道一套说法，
   改一处全局生效，模型不会在同一件事上收到矛盾描述。
5. **互斥闸**：结果只送一次；提交失败不标记消费（标记=丢结果）。
6. **等待让路**：block=true 期间检测插话让路，插话的送达点（模型调用）不被堵死。
