# 回合中插话

> 本页内容对应 README 的「回合中插话」章节。


一个回合可能有十几轮工具调用、跑好几分钟。而人在工具循环中途开口，十有八九是看它跑偏了想纠正——等事都做完再听，这句话就从「纠偏」降级成了「善后」。

过去只有两个出口：干等到底，或按 Esc 砍掉整个回合（连已经跑对的部分一起丢）。现在有第三条路：**不打断回合，把消息插进下一次模型调用**。

### 怎么用

| 你想 | 怎么做 | 等待 |
| --- | --- | --- |
| 尽快让模型看到 | 直接 Enter（默认） | 当前这一个工具跑完 |
| 等它忙完再说 | `/queue <消息>` | 整个回合结束 |
| 别跑了，听我的 | Esc | 立即；未送达的插话**放回输入框** |

「当前这一个工具跑完」这句话有一个例外要专门堵：`TaskOutput(block=true)` 本身就是**故意等下去**的（默认上限 300 秒），它一等就把这句承诺变成了空话。所以那个工具的轮询会顺路查插话队列、有就提前收工，见「后台子 agent → 结果怎么回来」。将来若再加别的「会长时间阻塞的工具」，同一根线得一起接上。

### 在界面上长什么样

和排队消息同一套：**没走的钉在输入框上方，走了才随信息流滚动**。

```
  › 帮我看看这个模块
⏺ Glob  {"pattern": "*"}
  ⎿ Glob ✓
  › 换个思路             ← 送达那一刻才打出来，位置正好在工具结果之后
  好，那我改成……

  ⤷ 还没送出去的那句      ← 未送达：钉在输入框上方，随时看得见
  › 等下回合再发的那句     ← /queue 排队的，在它下面
╭──────────────────────────────────╮
│ 输入框                            │
╰──────────────────────────────────╯
⏺ 运行 Glob… · 插话 1 条 · Esc 取消
```

两个面板的**上下顺序即送达先后**：插话随本回合下一次模型调用送达，排在上面；`/queue` 要等整个回合结束，排在下面。行首符号也不同（`⤷` vs `›`）——不然分不清自己那句话什么时候会被听见。

**输入那一刻刻意什么都不往对话区打。** 那时它还没送达，而对话区里的行事后改不了；打下去就永远停在「输入时」这个位置上，而它的真实位置在后面那条工具结果之后。送达时才由 `onUserMessage` 打进信息流——于是屏幕顺序、发给模型的消息表顺序、`-c` 回放顺序，三者一致。

状态栏另有一个 `· 插话 N 条` 实时计数（送达后该段消失），作为面板之外的第二条反馈。

### 什么时候会自动回落成排队

三种情况下按 Enter 仍然是「排到下回合」，不是插话：

- **压缩中**、以及**回合已被 Esc 取消、只剩子 agent 在收尾**——这两种状态不会再有模型调用，插话进去等于石沉大海
- **本条消息挂了技能**（`/skill`）——插话是一条纯 user 消息，带不了技能参数，走插话会静默丢技能

### 消息插在哪里

合法位置**只有一个**：所有工具结果之后。

```
system
user       原始提问
assistant  tool_calls
tool       工具结果
user       插话        ← 只有这里合法
```

落在 `assistant(tool_calls)` 与 `tool` 之间就是悬空 tool_calls，下一次请求直接被网关 400。而会话存储层**看不到**这个位置——工具结果落库与「构建下一次 prompt」是同一步，从存储层追加必然错位。所以注入挂在 ChatModel 装饰器层（`InterjectingChatModel`），那一层拿到的消息表已经配平。

插话送给模型时会被 `[interjection]` 包裹并附一句行为指引（大意：用户在任务执行中插话，未完成的工作仍在进行；与当前方向冲突就调整，否则先把手头的做完）。不包的话，模型在 tool 结果之后突然看到一条 user 消息，很容易判定「上一轮结束了，这是新任务」，于是丢下没做完的活去做新的、或者提前收尾。

回合结束时，这条插话会按锚点补进会话历史——否则它只活在那一次请求里，`-c` 恢复和压缩之后，历史上就会出现一次「无来由的转向」。

落进历史的是**包裹后**的文本，但 `-c` 回放时会被拆掉（`InterjectionText.unwrap`），只显示你说的那句原话——包裹里那段是**给模型的行为指引**，不是你说的。同类护栏 `<skill_instruction>` 与图片引用块也各有一份。

### 已知边界

- **模型对指引的实际反应未经真实 provider 验证**。冒烟用的是桩模型，它答不了「会不会真的按指引先把手头的做完」。指引措辞目前偏保守（倾向让它先做完再理你），若实际用下来插话基本都是要它立刻改道，改 `InterjectingChatModel.GUIDE`。
- **同一回合内插两次**，两条会被合并、锚点取最新那次，于是第一条在历史里的位置比它实际送达处略靠后。都在同一回合内，偏差有限，当前选择接受。
