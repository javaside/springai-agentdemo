# v1.32.0 — 智谱 GLM-5.4 接入（视觉 + 1M 上下文 + 默认旗舰）

在 [v1.31.0](v1.31.0.md) 基础上的**功能版**（minor）。核心交付物仍是终端编码智能体 **`springai-code-tui`**。

发布日期：2026-11-23。

本版接入智谱 2026-11-23 上线的新旗舰 GLM-5.4：视觉能力首次进入 GLM-5 系旗舰线、1M 上下文、
泛编码能力强化，并把它设为智谱 provider 的默认模型。单主题改动，按「测试先红后绿 → 全量测试 →
真机产物验证」执行。

## 一、GLM-5.4 接入

**模型事实**（官方切换指南核实）：`glm-5.4`，Loop Transformer 架构、约 7000 亿参数，新增视觉
输入能力，1M 上下文，Coding Plan 周额度为 glm-5.3 的 1.5 倍，泛编码能力强化。

**端点限制（本版最重要的使用注意）**：发布时 GLM-5.4 **仅在 Coding Plan 端点可用**
（`https://open.bigmodel.cn/api/coding/paas/v4`），常规按量付费端点官方口径为「完成安全评估后
上线」。本项目的默认 base URL 仍是常规端点（双端点计费池分离，切默认会坑按量付费用户），因此：

- Coding Plan 订阅用户：配置 `ZHIPU_BASE_URL=https://open.bigmodel.cn/api/coding/paas/v4`，
  glm-5.4 即为默认模型，开箱即用。
- 按量付费用户：默认模型 glm-5.4 在常规端点暂不可用，请经 `ZHIPU_MODELS` 把首项换回
  `glm-5.3`，或等待官方开放常规端点。

以上两点已写入 `config.env.example` 的注释（`ZHIPU_BASE_URL` 段与 `ZHIPU_MODELS` 示例行）。

**思考能力与 glm-5.3 系同构**：服务端把 `thinking.type` + `reasoning_effort` 映射为 low/high/max
三档，「关闭思考」的任何取值实际也落到 low——即不可真正禁用。本项目按此登记：effort 三档、
不支持 disabled、非法档位拒绝。

**五处同步点**（按新模型接入清单逐项核对，v1.25.0 漏改 `config.env.example` 教训的完整执行）：

| 同步点 | 改动 |
| --- | --- |
| `ZhipuProvider.MODELS` | `glm-5.4` 置首（默认旗舰）+ `thinkingCapabilities` 补 effort 分支 |
| `ModelContextWindows` | `zhipu:glm-5.4` → 1,000,000（官方建议的 512000 压缩窗口属另一层参数，由压缩器自行校准） |
| `VisionModels` | 精确前缀 `glm-5.4`（不能用宽前缀——glm-5.3 仍是纯文本，会误伤） |
| `config.env.example` | `ZHIPU_MODELS` 示例行 + coding 端点提示 |
| `docs/guide/vision.md` | 智谱视觉前缀行与内置清单注记 |

**默认模型切换是刻意的**：glm-5.4 置于清单首位即默认模型，为 2026-11-23 发布当天经用户拍板的
显式变更（当时已知按量付费用户需自配端点或换回 glm-5.3）。

## 二、验证

**测试先红后绿**：先改 8 处断言（清单/默认模型/视觉能力/上下文窗口/thinking 档位）跑出 8 处预期
失败，失败原因全部是「glm-5.4 未接入」本身；实现后转绿。全量 **2578 例 0 失败**（20 例环境变量
门控跳过）。全量测试还兜住了一处 grep 漏掉的既有默认断言（`ProviderModelsEnvTest`），同步校准。

**产物验证**：从打包后的 jar 逐类核验字节码——`ZhipuProvider` 含 `glm-5.4`（清单与 thinking
分支）、`VisionModels` 含 `glm-5.4` 前缀、`ModelContextWindows` 含 `zhipu:glm-5.4`。

**遗留人工项**：glm-5.4 的视觉与编码能力真机体验待用户环境验证；官方开放常规端点后需回收
`config.env.example` 与 `ZhipuProvider` 注释中的「仅 coding 端点」提示。
