# springai-agentdemo v1.21.1

在 [v1.21.0](v1.21.0.md) 基础上的**修订版**（patch）。核心交付物仍是终端编码智能体 **`springai-code-tui`**。

本版两个修复，均源自排查一份真实用户报告——"子 agent 好像一直在用 TodoWrite，主 agent 却完全不用，感觉不对"。排查结论：不是路由/派发 bug，是两处已有设计的叠加效果：**① `general-purpose` 子 agent 默认拒绝 TodoWrite**——子 agent 调用该工具的完整内容此前就会被 UI 有意丢弃，只在 scrollback 留一行面包屑，继续默认放行只是让子 agent 白白多花一次工具往返；**② `-c` 恢复会话时重建 todo 面板**——此前恢复只回放 scrollback 文本，从不重建 todo 面板，面板会一直空白直到主 agent 恰好再调一次 TodoWrite（真实会话里它靠读 report 文件和 git 状态另行恢复了进度认知，但面板本身从未重新出现过内容）。

**下载物：** 两个自包含运行包 `springai-code-tui-1.21.1-dist.tar.gz`（macOS / Linux 首选）/ `springai-code-tui-1.21.1-dist.zip`（Windows 首选），解压即用、无需构建，内容与惯例一致：启动脚本（`bin/`）+ 主 jar + 全部运行期依赖（`lib/`）+ 配置示例 + 使用指南 + `LICENSE`/`NOTICE`/`README`。运行时界面版本标识为 **`v1.21.1`**。SHA-256 校验和见文末「发布前验证」。

> 完整功能全景与安全声明见 [v1.3.0 发布说明](v1.3.0.md) 与 [v1.0.0 发布说明](v1.0.0.md)；本文只列出相对 v1.21.0 的变化。

## 修复：`general-purpose` 子 agent 默认拒绝 TodoWrite

内置四个子 agent（`general-purpose`/`explore`/`plan`/`bash`）里，只有 `general-purpose` 此前默认能拿到 TodoWrite——另外三个用白名单式 `tools:`，TodoWrite 从未在列。子 agent 调用 TodoWrite 时，`ConversationState.onTodoUpdated` 会按 `taskId` 分流：主 agent 自己的调用才会写进可见的 todo 面板，子 agent 的调用（`taskId != null`）**内容会被直接丢弃**，UI 上只留一行 `⎿ TodoWrite ...` 面包屑，完整清单从未渲染到任何地方——这是有意的设计（避免多个并发子 agent 的内部清单把面板刷成噪音），不是本次改动的对象。

既然内容注定不可见，继续默认放行就是让子 agent 白白多花一次工具往返。现在 `general-purpose.md` 的 `disallowedTools` 从 `AskUserQuestionTool` 扩成 `AskUserQuestionTool, TodoWrite`。用户自定义的子 agent（`agents/*.md`）不受影响——这只是改内置默认值，不是全局硬限制。

## 修复：`-c` 恢复时重建 todo 面板

`ConversationState.replayHistory`（`-c` 恢复启动时调用）此前只把历史转成 scrollback 文本，从不重建 todo 面板——恢复那一刻面板必然是空的，直到主 agent 在新会话里**再次**调用 TodoWrite 才会重新出现内容。真实会话里，主 agent 恢复后改用读 `report.md` 文件和 git 状态来重建进度认知（这条路径本身是对的、也更可靠——真正的计划状态本就该以文件产物为准），但代价是面板从此以后就一直空着，跟 scrollback 里不断刷出的子 agent 活动面包屑放在一起看，观感就是"子 agent 一直在用、主 agent 完全不用"。

现在 `HistoryReplay` 新增 `lastTodoSnapshot(List<Message>)`：扫描历史找最后一次 TodoWrite 调用、反序列化其参数，复用既有的 `AgentTools.toLines`（格式化逻辑，现升为 `public` 供跨包调用）转成显示行——与实时面板用的是同一份格式化代码，不会跑偏。`ConversationState.replayHistory` 在原有恢复逻辑里追加把这份快照写进 `todo` 字段。找不到任何 TodoWrite 调用、或参数反序列化失败（容忍老版本残留数据），一律静默返回空列表，不让恢复流程崩掉——这条路径不会、也不可能混入子 agent 的 TodoWrite：子 agent 每次委派都是无会话记忆的一次性 `ChatClient` 调用（见 `SubagentRunner.execute`），其内部工具调用从不写入主会话的持久化消息流，历史里扫到的 TodoWrite 调用结构上就保证全部来自主 agent 自己。

## 测试

两处均按 TDD（先红后绿），走完整 brainstorming → 设计 → 计划 → subagent-driven-development 流程，每个任务独立 spec 合规审查 + 代码质量审查两阶段把关，全部实施完成后再加一轮覆盖两处组合效果的整体审查：

- **`general-purpose` 拒绝 TodoWrite**：`SubagentDefinitionsTest` 新增回归断言，钉住 `general-purpose` 的 `denyTools()` 包含 `"TodoWrite"`。代码质量审查发现 `implementation-map.md` 有一处描述子 agent 工具约束的旧文字没有跟着更新，已同批修正。
- **`-c` 恢复重建 todo 面板**：`HistoryReplayTest` 新增 3 例（确定性钉住"多次调用取最后一次""无调用返回空""参数格式异常容错返回空，不抛异常"），`ConversationStateTest` 新增 2 例（端到端验证 `replayHistory` 后 `todoSnapshot()` 确实反映历史、无 TodoWrite 时面板保持空）。代码质量审查额外做了变异测试（临时把新方法改回空实现，确认新测试真的会红）核实测试不是摆设。
- **整体审查**新发现 2 处遗漏（均为文档，非代码/行为）：`implementation-map.md` 缺了 `lastTodoSnapshot` 机制说明；`AgentListener.java` 一段预先存在、但恰好描述反了本次改动核心机制的 javadoc（哪个 taskId 进哪个面板说反了，且误称子 agent 的 todo"会显示"——实际是被丢弃）。两处均已修正并通过复核。

## 升级说明

**无配置变更，无破坏性变更。** 直接替换运行包即可。升级时请先退出旧进程，再替换文件并重新启动。

- 两处都是修复，不涉及任何用户可见的配置项。`general-purpose` 子 agent 少了 TodoWrite 后行为不变——它的活动仍会在 scrollback 逐行展示，只是不再徒劳地把不可见的清单内容再写一遍。
