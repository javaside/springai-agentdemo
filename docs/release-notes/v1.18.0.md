# springai-agentdemo v1.18.0

在 [v1.17.1](v1.17.1.md) 基础上的**功能版**（minor）。核心交付物仍是终端编码智能体 **`springai-code-tui`**。

> 说明：v1.17.2 在发布准备完成后发现仍有后续改动，未正式发布；其内容（「输出中打字」卡死修复）并入本版。

本版主题是 **`/context` 上下文占用透明化**：报告从「事件数 / token」两行升级为分类明细——事件按用户/助手/工具分桶，token 口径统一为「上下文占用」（系统提示词 + 会话消息，即每回合真实发出去的量），构成逐行展示各项占比，总和恒为 100%。同时补齐**工具调用健壮性**（报错不再毁掉整回合，而是把错误原因回给模型自纠），并把长期记忆系统提示精简掉 34% token。

**下载物仍是两个自包含运行包（解压即用，无需构建）：**

- `springai-code-tui-1.18.0-dist.tar.gz`（macOS / Linux 首选）
- `springai-code-tui-1.18.0-dist.zip`（Windows 首选）

两者内容一致：启动脚本（`bin/`）+ 主 jar + 全部运行期依赖（`lib/`）+ 配置示例 + 使用指南 + `LICENSE`/`NOTICE`/`README`。运行时界面版本标识为 **`v1.18.0`**。

> 完整功能全景与安全声明见 [v1.3.0 发布说明](v1.3.0.md) 与 [v1.0.0 发布说明](v1.0.0.md)；本文只列出相对 v1.17.1 的变化。

## 新功能：`/context` 上下文占用分类明细

此前 `/context` 只报事件数与 token 两行，构成不可见：系统提示词占多少、消息占多少、压缩阈值怎么算，全都对不上账。本版重做报告结构：

- **事件分桶**：`事件数：N 条（用户 n · 助手 n · 工具 n · 其他 n）`，一眼看出消息类型分布。
- **唯一总数口径「上下文占用」**：`上下文占用：X / Y token（占窗口 Z%）`——总数 = 系统提示词 + 会话消息，就是当前上下文里躺着的全部 token，也是每回合真实发出去的量；占窗口百分比与状态栏「上下文 N%」同一分母，两处不再互相矛盾。
- **构成逐行展示**：系统提示词、用户消息、助手消息、工具结果（有摘要时加「系统/摘要」）逐行列出 token 数与占比；占比用 largest remainder 分配，**合计恒为 100%**（各自四舍五入会得 99%/101%，又对不上账）。系统提示词行标注「每回合固定重发」——它是烘焙在 ChatClient 里、从不进会话存储的那笔开销，单独列账才能解释「为什么请求比会话估算大」。
- **自动压缩行**：阈值按「会话消息」（不含系统提示词）判定——压缩删的也是消息，系统提示词不在其列；分子写原值，与构成里的消息项之和对得上账。

### 设计要点（为什么这样报）

- **系统提示词并入总数而非单独一行**：系统提示词从不进会话存储，单列「会话估算」行会与总数互相矛盾（两行数字不同，用户无从对账）。唯一口径 = 系统提示词 + 会话消息。
- **占比不各自四舍五入**：5 项各自 round 得 99% 或 101%，又是对不上账的源头。largest remainder 把余量按小数部分从大到小各补 1%，每项落在自己的 floor/ceil 之间、永不越界。
- 报告只读实时快照、任何时刻可查；尚无对话时各项为 0，明确提示「尚无对话历史」。

## 修复：工具调用报错不再毁掉整回合

模型在工具调用链路中出现两类失败时，Spring AI 默认行为是抛异常把整回合标成失败（白白浪费一次调用）：

1. **工具名拼错**（`No ToolCallback found`）：DeepSeek 偶发把工具名拼错（如 `BochaWebSearch` → `BoochaWebSearch`），Spring AI 按名精确匹配失败直接抛 `IllegalStateException`。
2. **工具执行异常**（`ToolExecutionException`）：工具内部抛错（含 Error 类 cause，如运行中替换 jar 导致的类加载错乱），默认处理器对部分异常 rethrow 终止回合。

修复（不新增别名工具、不污染模型可见的工具清单）：

- `ResilientToolCallingManager`：包装默认 ToolCallingManager，捕获「No ToolCallback found」异常，改为把「工具 X 不存在。请使用正确的工具名重新调用。」作为工具结果回给模型，模型自纠后回合继续。刻意不列可用工具清单——工具清单本就随请求发给模型，再列是重复噪音。
- `ResilientToolExecutionExceptionProcessor`：自定义异常处理器，工具执行异常转成错误文本回给模型（异常类型 + 消息 + 完整 cause 链 + 关键堆栈前 6 帧），不附加引导词；**绝不 rethrow**。
- 顺带修复一个相关 bug：MCP 工具为空时不调 `.tools()`（传空数组在 Spring AI 2.0 下会**覆盖** defaultTools，使内置工具在本请求的解析器里不可见——MCP 尚在后台连接的头几秒，模型一调内置工具就报「No ToolCallback found」）。

后续两个提交继续打磨这条链路：

- **工具名解析失败区分「不存在 / 可解析未执行」**：不再把「解析成功但未执行」误报成「工具不存在」——模型拿到的是准确状态，不会在正确的工具上反复重试。
- **解析失败补偿按位置精确报告执行状态**：失败补偿信息精确到发生位置，模型不再被误导（此前在部分顺序错乱场景会误判哪个工具没跑）。

## 性能：长期记忆系统提示精简，system prompt 省 34% token

上游 spring-ai-agent-utils 0.10.0 的 `AUTO_MEMORY_TOOLS_SYSTEM_PROMPT.md` 有 10.9KB / ~2400 token，是整份 system prompt 的最大头（65%），其中大半是 8 组对话示例与冗长说明。

在项目 resources 放同路径**精简版**覆盖 jar 内上游版（classpath 顺序优先，加载逻辑零改动）：保留工具表、frontmatter 格式契约、四类记忆与保存/清理规则，删掉示例与重复解释；另把「动手前查技能清单」「需求未定须提问」的引导写进系统提示词，避免表述明确但设计未定的请求直接动手导致返工。

> 精简只影响**长期记忆段**；其余系统提示段（工具访问边界、技能引导等）不变。若将来升级 spring-ai-agent-utils，需重新 review 覆盖文件是否仍与新上游一致。

## 修复：输出中打字不再卡死 / 终端崩溃

> 本段为 v1.17.2 准备的内容，因 v1.17.2 未正式发布，并入本版。

### 症状

- 模型**长输出期间**在输入框打字，界面周期性卡顿（输入无响应、画面定格数秒），严重时**整个终端意外退出**（macOS Terminal.app 崩溃报告：`EXC_BAD_ACCESS`，崩溃线程在 `NSTextInputContext` / `IMKInputSession`——输入法合成被高频 ANSI 刷新打断）。
- 会话历史很大的情况下（实测 1MB+ 的会话），即使不输出，状态栏刷新也会周期性冻结界面。

### 根因（三个叠加）

1. **渲染线程上的 token 估算**：状态栏上下文用量每 ~1s 全量重算（遍历全部消息 + jtokkit 分词估算）。大会话下单次耗时数百 ms，且跑在**渲染线程**上——期间输入、重绘、按键全部冻结。实测会话历史 1.3MB 时每 ~1s 卡一次约 300ms。
2. **无限增长的流式残行**：模型输出长时间不换行时，`streaming` 缓冲无限累积（实测出现**百万字符单行**）。渲染线程**每帧**都对整段残行做预览 + 语法高亮 + 折行——O(百万) 的每帧字符串操作，把渲染线程拖死。用户一打字（事件排队）就表现为卡死。
3. **高频全量重绘**：默认 tick 40ms（≈25fps 全屏重绘）+ scrollback 下沉 33ms。内容每帧在变时（流式输出中）diff 挡不住，叠加到 Terminal.app 上冲击输入法合成 → 终端崩溃。

### 修复方式

1. **token 估算移出渲染线程**（`CodeTuiView`）：状态栏上下文用量改在独立 daemon 线程（`context-usage-refresh`）刷新，渲染线程只读 volatile 快照——大会话不再周期性冻结界面。
2. **流式残行上限 20 万字符**（`ConversationState`）：超过上限把多余部分切行下沉定稿（一次性），残行预览永远只面对 ≤20 万字符。
3. **渲染降频**（`CodeTuiView`）：tick 40ms → **100ms**（10fps），scrollback 下沉 33ms → **66ms**——输出中的 ANSI 频率大降，冲击输入法合成的概率随之大降。
4. **残行预览节流**（`CodeTuiView`）：流式残行预览只允许每 ~150ms 更新一次，不再每帧重写预览行。

### 说明

- 本版无法根治 **Terminal.app 自身的输入法崩溃 bug**（`NSTextInputContext` 空指针，崩溃栈中无 code-tui 帧）。降低 ANSI 输出频率能显著降低触发概率；若仍频繁崩溃，建议换用输入法处理更稳的 iTerm2。
- 运行中**替换发布 jar** 会导致 JVM 类加载索引与磁盘不一致，出现「类明明在 jar 里却 ClassNotFoundException」的假象（如 `OptionSpec`）。升级请**先退出旧进程，再替换文件，最后启动**。

## 质量

发布前验证：

- `mvn -pl springai-tamboui-inline-patch test` → **Tests run: 35, Failures: 0, Errors: 0**
- `mvn -pl springai-code-tui -am test` → **Tests run: 1615, Failures: 0, Errors: 0, Skipped: 10**（10 个 skipped 全部为 env 门控的真机探针；`-am` 必带——本模块依赖同仓库不发布的兄弟模块）
- `mvn -pl springai-code-tui -am clean package -Pdist` → BUILD SUCCESS

本版新增验证手段：

- `/context` 报告结构：`ContextUsageTest` 覆盖事件分桶、上下文占用总数口径、构成逐行占比（含 largest remainder 合计恒 100% 断言）、系统提示词单列、缓存命中率行。
- 工具调用健壮性：新增 7 个测试（拼错→返回纠正结果且不含「可用工具」、非解析异常原样抛、正常透传、异常处理器类型/消息/cause 链/堆栈帧截断），后续提交补「不存在/可解析未执行」区分与按位置补偿的回归。
- 长期记忆精简：`MemoryPromptTest` 断言覆盖文件生效且系统提示 token 大幅下降。

## 升级说明

**无破坏性变更**。`config.env` 可直接沿用，无需新增环境变量。行为变化只有两处：`/context` 报告结构重做（旧的两行式不再有），以及工具调用失败时**不再终止回合**——此前某工具失败整回合报错退出的场景，现在会看到模型收到错误原因后自行重试或换路，属预期改进。
