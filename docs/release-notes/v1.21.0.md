# springai-agentdemo v1.21.0

在 [v1.20.1](v1.20.1.md) 基础上的**功能版**（minor）。核心交付物仍是终端编码智能体 **`springai-code-tui`**。

本版三件事：**① 子 agent 支持按次覆盖模型**——委派 `Task`/`ParallelTasks` 时可选 `model` 参数，让某一次委派跑在跟主 agent 不同的模型上（典型用法：同一份材料派给不同模型的子 agent 分别评估、再综合对比），跨 provider 精确路由，未知模型清楚报错，scrollback 与任务面板显示每次委派实际用的模型。**② 根治"输出时打字卡死"的又一次复发**——9 月 3 日的 `AsyncPtyWriter` 修复解决了 pty 写阻塞，但表格排版与 diff 展开这两处已知的预算例外，会在一批里连续多次调用 `drain()` 时各自重新豁免一次，跨段叠加；现在豁免只在整批第一次真正消费内容时生效一次。**③ 收紧模型覆盖的使用边界**——真实会话实证：主 agent 曾在连续两次网络瞬时故障后自作主张切换模型，工具描述现在明确禁止这种用法。

**下载物：** 两个自包含运行包 `springai-code-tui-1.21.0-dist.tar.gz`（macOS / Linux 首选）/ `springai-code-tui-1.21.0-dist.zip`（Windows 首选），解压即用、无需构建，内容与惯例一致：启动脚本（`bin/`）+ 主 jar + 全部运行期依赖（`lib/`）+ 配置示例 + 使用指南 + `LICENSE`/`NOTICE`/`README`。运行时界面版本标识为 **`v1.21.0`**。SHA-256 校验和见文末「发布前验证」。

## 功能：子 agent 按次覆盖模型

**用例**：主 agent 委派子任务时，此前子 agent 只能跟主 agent 用同一个模型。现在 `Task`/`ParallelTasks` 新增可选 `model` 参数（`"provider:modelId"`），主 agent 可以把同一份材料并发派给不同模型的子 agent 分别评估，再综合各家反馈改进——比如让 DeepSeek 和 Claude 各自审一遍同一份设计文档，对比两边的意见。

- **格式**：`"provider:modelId"`（如 `deepseek:deepseek-chat`）精确跨家路由；裸 `modelId`（无冒号）按「第一个拥有该 id 的 provider」宽松匹配，兼容旧写法。省略该参数（或留空）= 跟随主 agent 当前激活的模型，行为与升级前完全一致。
- **只在这一次委派生效**：不改子 agent 定义文件（`agents/*.md`）里的默认模型，也不改全局的"当前激活模型"——`ParallelTasks` 里的多个子任务可以各自指定不同模型，互不影响，也不会影响主 agent 自己。
- **未知/不可用模型清楚报错**：不会静默退回到当前激活模型。这本身是一个顺带修复的 bug——`ProviderRegistry.requestSelection` 此前两个分支殊途同归，跨 provider 的 `modelId` 曾被悄悄按当前激活模型跑掉，模型换了个名字用户却毫无感知；现在两个重载找不到对应 provider/model 都直接抛出清楚的错误。
- **界面可见性**：scrollback 与任务面板（含"⏱ 后台任务"面板）都会显示每次子 agent 委派**实际请求的模型标签**，不用再去猜某次委派到底跑的是哪个模型。
- **工具描述里带模型清单**：`Task`/`ParallelTasks` 的描述会列出当前所有可用的 `provider:modelId`，供主 agent 挑选。

设计与实施经完整 brainstorming → 设计 → 计划 → 实施流程，每个任务独立 spec 合规审查 + 代码质量审查两阶段把关（含一轮真实发现的测试假阳性修正：跨 provider 覆盖的回归测试最初用了不会撞车的 modelId，旧 bug 代码也能碰巧通过，改用同名 modelId 撞车重新验证）。

## 修复：drain 批时间预算跨段共享（"输出时打字卡死"再次复发）

**事故形态**：用户报告"模型输出文字时，输入框打字仍会卡死"——这个症状 9 月 3 日刚做过一次彻底修复（`AsyncPtyWriter`：把 pty 的 `write(2)` 剥离到独立守护线程，根因是内核 pty 写缓冲仅 1-2KiB、终端读端停摆时 write 无界同步阻塞）。排查首先重跑了那次修复的三个回归测试（含专门钉"pty 写卡死期间按键 1 秒内被处理"的症状测试），仍然全绿——**pty 写阻塞这条根因没有回归**，是另一个不同的机制。

**根因**：渲染批的"300 物理行 / 12ms"双预算里，两处已知且刻意接受的例外——diff 展开的 LCS 计算与 markdown 表格的整块排版——都发生在拿到第一行输出之前、时间检查够不着的地方，单独看成本都不大（实测 diff 800×800 行约 16.5ms、表格 200 行约 13ms）。真正的缺口是：`PhysicalOutputQueue.drain()` 里判断"是否豁免"的计数器是**每次调用都从 0 重新计**的局部变量，而 `CodeTuiView` 一批最多调用它 3 次（主段、计划段、回合结束强制表格 flush 段）——每一段都能各自重新拿到一次豁免，两处例外的成本因此可以跨段叠加。

**修复**：`drain()` 新增 `alreadyWrittenThisBatch` 参数，豁免判断从"本次调用局部 written≥2"改成"整批累计 alreadyWrittenThisBatch+written≥2"，调用方传入既有的 `batchRowsUsed` 字段即可——不改任何既有上限常量（300 行 / 12ms / 表格 200 行 64K 字符 / diff 800 行都不变），只改账目算法本身。

配套的确定性单测（假游标 + 显式过期 deadline，不依赖真实墙钟）证明了修复前后的行为差异；一条真实内容驱动的端到端集成测试（大 diff + 未闭合大表格同现一次回复）也补充了内容完整性与粗粒度性能兜底，但排查中变异测试证实：这条端到端用例本身测不出这个 bug 的精确回归（它的真实成本增量只有约 1 行写入，微秒级，不是"几百毫秒"）——真正的回归哨兵是前面那条确定性单测。

## 小修：收紧模型覆盖的使用边界

真实会话实证：主 agent 连续两次因网络瞬时故障（HTTP/2 流中断）派发子 agent 失败后，自行决定"换个更稳定的模型重试"——用户全程没有要求切模型，换的模型还返回 403 又再换了一次。`Task`/`ParallelTasks` 的工具描述此前只讲"怎么用 `model` 覆盖"，没讲"什么时候才该用"，容易被合理化成故障排除手段。

现在工具描述（以及 `model` 参数自身的说明）都明确加了两条纪律：只有用户在当次请求里明确要求指定模型或跨模型对比时才该设置 `model`；网络超时、流中断、网关 5xx、限流这类瞬时故障不是换模型的理由，应该原地重试同一个 dispatch。这是纯 prompt/描述层面的约束，不是代码路由逻辑的改动（路由逻辑本身没有 bug，验证过 `requestSelection` 全程只读不写全局状态）。

## 测试

三件事均按 TDD（先红后绿），且都有独立的 spec 合规审查 + 代码质量审查：

- **模型覆盖**：`ProviderRegistryThinkingTest`（跨 provider 路由、未知模型抛错）、`SubagentRunnerThinkingTest`（跨家覆盖路由到正确 provider，含用同名 modelId 撞车的严格版回归测试）、`SubagentToolTest`（schema 暴露 `model` 参数、描述列出模型清单、批量委派各子任务独立覆盖）、`ConversationStateTest`/`ConversationStateBackgroundTest`（前台/后台面板显示模型标签，含模型标签内嵌换行被正确折叠单行的回归测试）。
- **drain 批预算**：新增 `PhysicalOutputQueueTest`（4 例，确定性钉住"批的第一段保留豁免、后续段不再重新豁免"）、`DrainBurstCapTest` 新增端到端集成用例。
- **模型使用边界**：`SubagentToolTest` 新增两条内容断言测试，钉住工具描述里"只在用户明确要求时用 model""瞬时故障不是换模型理由"这两条纪律的文本存在。

## 升级说明

**无配置变更，无破坏性变更。** 直接替换运行包即可。升级时请先退出旧进程，再替换文件并重新启动。

- 模型覆盖是纯新增的可选参数，不设置就是升级前的行为；drain 批预算修复对用户完全透明；模型使用边界收紧只影响主 agent 的工具调用决策，不改任何用户可见的配置项。
- 受影响场景：使用 `Task`/`ParallelTasks` 委派子任务、且回复中包含表格或大量文件 diff 的场景最能感受到本版改动。
