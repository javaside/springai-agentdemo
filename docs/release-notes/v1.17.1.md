# springai-agentdemo v1.17.1

在 [v1.17.0](v1.17.0.md) 基础上的**修订版**（patch）。核心交付物仍是终端编码智能体 **`springai-code-tui`**。

本版唯一主题：**根治行内 TUI 卡死**。此前在 `/model` 切换模型、以及对话输入后，界面可能永久定格——任何按键（输入框打字、选择器回车）一概失效。本版定位到根因是事件循环对异常零防护，通过 shadow 补丁让渲染线程永不因一次按键处理异常而死亡。

**下载物仍是两个自包含运行包（解压即用，无需构建）：**

- `springai-code-tui-1.17.1-dist.tar.gz`（macOS / Linux 首选）
- `springai-code-tui-1.17.1-dist.zip`（Windows 首选）

两者内容一致：启动脚本（`bin/`）+ 主 jar + 全部运行期依赖（`lib/`）+ 配置示例 + 使用指南 + `LICENSE`/`NOTICE`/`README`。运行时界面版本标识为 **`v1.17.1`**。

> 完整功能全景与安全声明见 [v1.3.0 发布说明](v1.3.0.md) 与 [v1.0.0 发布说明](v1.0.0.md)；本文只列出相对 v1.17.0 的变化。

## 修复：行内 TUI 不再因一次未捕获异常而永久卡死

### 症状

- 在 `/model` 模型选择界面切换模型时，长时间不选择，之后再回车无法确认——输入框也无法输入。
- 对话界面输入后停在「思考中」，界面定格、任何按键失效。

两者表象不同，根因同一：**TUI 渲染线程（即事件循环线程）被一次未捕获异常杀死**，但 `running` 标志仍为 `true`，输入线程继续往事件队列投递按键却无人消费——于是界面永久定格。

### 根因

内部依赖 `dev.tamboui:tamboui-tui:0.4.0` 的 `InlineTuiRunner.run()`（行内版事件循环）对 `handler.handle()` 与 `UiRunnable.run()` **没有任何 try-catch**。对照全屏版 `TuiRunner.run()`，两者都有 `try{...}catch(Throwable){...; continue;}` 防护，唯独行内版漏了。

一旦 UI 按键处理链（`CodeTuiView.onInputKey → onModelPickerKey / onAskKey / …`）抛出任何未捕获 `RuntimeException`（最典型是 `% n` 除零——当 `/model` 打开后模型列表为空 `n==0`，按 ↑/↓/j/k 即触发 `ArithmeticException`），异常直接逃出 `while(running.get())` 循环 → 渲染线程终结。

### 修复方式

在 `springai-tamboui-inline-patch` 模块新增**同包同名 shadow 类** `dev.tamboui.tui.InlineTuiRunner`。依赖 classpath 顺序（该模块 jar 排在 `tamboui-tui` 之前，已在运行时用探针验证 JVM 优先加载 patch 版）覆盖原版，仅做一件事：

- 给事件循环里的 `handler.handle` 与 `UiRunnable.run` 各包一层 `try(Throwable)`，捕获后记录日志并 `continue`。

效果：**渲染线程永不因 handler 异常死亡**。异常被记录到日志（可诊断）后，事件循环照常处理后续按键——`/model` 选择器、输入框、回车全部恢复可用。构造/生命周期逻辑与原版逐字一致，无其他行为变化。

> 说明：本版只治「异常不再卡死 UI」这一层。`onModelPickerKey`/`onSkillPickerKey`/`onAskKey` 里的 `% n` 除零守卫、以及发送路径的同步段兜底，属于「消除异常源」的加固，本版未一并修改——现在它们即便仍会抛异常，也只会被事件循环捕获并记一条 SEVERE 日志，不再卡死界面。

## 升级说明

**无破坏性变更**。`config.env` 可直接沿用。无需新增环境变量。

本次改动仅在构建期补齐了 `springai-tamboui-inline-patch` 模块对 `tamboui-tui` 的编译依赖（单向、无循环），用于让 shadow 类可编译；运行期行为不变，仅多了异常防护。
