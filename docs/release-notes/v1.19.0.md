# springai-agentdemo v1.19.0

在 [v1.18.3](v1.18.3.md) 基础上的**功能版**（minor）。核心交付物仍是终端编码智能体 **`springai-code-tui`**。

本版两件大事：一是**界面更新彻底改事件驱动**——删掉常驻的定时重绘与 drain 轮询，改成「有变化才画」的合并通知，空闲时终端零周期输出，这是 v1.18.3 物理行限速的延续与深化；二是**智谱视觉模型全面接入**——`glm-5.3-flash`（GLM-5 系首个原生多模态）入内置清单，视觉名单补 `glm-4.6v` / `glm-5v` 前缀，上下文窗口、thinking 档位、真机冒烟探针一并补齐。

**下载物为两个自包含运行包（解压即用，无需构建）：**

- `springai-code-tui-1.19.0-dist.tar.gz`（macOS / Linux 首选）
- `springai-code-tui-1.19.0-dist.zip`（Windows 首选）

两者内容一致：启动脚本（`bin/`）+ 主 jar + 全部运行期依赖（`lib/`）+ 配置示例 + 使用指南 + `LICENSE`/`NOTICE`/`README`。运行时界面版本标识为 **`v1.19.0`**。

> 完整功能全景与安全声明见 [v1.3.0 发布说明](v1.3.0.md) 与 [v1.0.0 发布说明](v1.0.0.md)；本文只列出相对 v1.18.3 的变化。

## 重构：界面更新改事件驱动

### 之前的问题

UI 一直在**周期性地干活**，哪怕界面没有任何变化：渲染线程挂着常驻 `tickRate(100ms)` 全量重绘，另有 `scheduleRepeating(66ms)` 的 drain 轮询定期把输出队列里可能为空的批次画出去。空闲时终端也在周期性输出 ANSI（远程/慢终端上尤其扎眼），高频 token 流又按「一个 token 一个 UI 任务」排队，渲染被高频事件塞满。

### 改法

`ConversationState` 与 agent 各组件**保持「持久真相源」不变**，只是不再被轮询；它们改为向新增的 `UiUpdateCoordinator` 发布**无锁 dirty 信号**（只带脏类别，不搬数据）。协调器把并发变化**合并**后，在 TamboUI 单线程上排**一次性任务**——常驻 tick 全部消失，各动态区改为按需一次性调度：

- 流式输出 continuation：排空到输出队列见底即停，不空转
- 预览唤醒：有唤醒事件才续帧，杜绝静态预览被反复重排
- 缩放稳定（resize settle）：停稳后一次性整屏重放
- 状态栏波光动画：续帧由自身一次性定时驱动，不再常驻
- 上下文占用刷新：防抖 + single-flight

物理行输出预算在 v1.18.3「按物理行计」的基础上继续细化：改为 **segment 级懒折行**（只有要打的那一段才折行）、**预折行尾部记录**（被打断的折行行从尾部续打不重打）、**共享 drain 预算**（各输出源共用一个预算，谁都不会把单帧打爆）。

配套的 `springai-tamboui-inline-patch`（仓库内 TamboUI 0.4.0 shadow 补丁）新增 **coalesced active redraw** 原语：`requestUiUpdate(action)` / `requestRender()` 线程安全、可合并、一次 wake 最多画一次、关闭后变 no-op，被同一 wake 事件收拢的多个 action 只触发一次 draw。

### 顺带修掉的一批竞态

- 状态栏波光续帧竞态：一次性定时任务执行前未清自身槽位，UI 批在 timer 回调返回前续排时误判旧 future 仍在飞，动画链停在首帧
- 静态预览反复重排：零延迟重启预览会把调度链无限续排
- continuation 折行续排的悬挂缩进丢失（N-1）
- subagent 计数发布遇 `Error` 直接顶掉整批发布
- modal 失败变更晚于外部响应发布，外部先看到旧状态

**对使用者**：无任何配置或行为变化——所有命令、面板、排队/插话/后台优先级、缩放重放、IME 修复照旧；区别是**空闲终端不再有周期性输出**，输出/输入并发更公平，高 token 速率下 UI 不再被单帧塞满。

## 功能：智谱视觉模型全面接入

### `glm-5.3-flash` 入内置清单（原生多模态）

2026-08-26 发布的 `glm-5.3-flash` 是 **GLM-5 系首个原生多模态模型**（视觉 + 编码），1M 上下文，价格约为旗舰的 **1/10**，性能超 `glm-5.2`。本版把它加入智谱内置清单（`/model` 可直接切换，描述标注「原生多模态 · 视觉+编码 · 1M 上下文 · 1/10 价」）。

**默认模型仍是旗舰 `glm-5.3` 不变**——加模型不悄悄改默认，已存偏好与新项目都不受影响。

### 视觉名单补三个前缀

`VisionModels` 前缀名单新增（2026-09-01 核实）：

| 前缀 | 说明 |
| --- | --- |
| `glm-4.6v` | 2025-12 上线，首个原生 Function Call 的视觉线（含 `glm-4.6v-flash` 免费档） |
| `glm-5.3-flash` | GLM-5 系首个原生多模态（**注意：`glm-5.3` 本身仍是纯文本**） |
| `glm-5v` | GLM-5V 系（2026-04 的 GLM-5V-Turbo，多模态 Coding 基座） |

关键防误伤测试一并补上：`glm-5.3` / `glm-5.2` / `glm-5.1` / `glm-5-turbo` 这些纯文本旗舰**不**因前缀相似而拿到视觉能力，裸 `glm-5` 也不匹配 `glm-5v`。

### 内置上下文窗口

`ModelContextWindows` 新增三条（2026-09-01 官方文档核实）：`glm-5.3-flash` **1M** / `glm-4.6v` **128K** / `glm-4.5v` **64K**。`glm-4v` / `glm-4.1v` 窗口未核实、不进表，落保守兜底（可用 `CODETUI_CONTEXT_WINDOWS` 覆盖）。压缩器不再把这些视觉模型按小窗口误判、频繁误触发自动压缩。

### thinking 档位与真机验证

- `glm-5.3-flash` 的 thinking 参数与 `glm-5.3` 一致（官方文档）：`thinking.type` 仅支持 `enabled`，`effort` 三档 `low` / `high` / `max`。
- 新增**智谱视觉真机冒烟探针** `ZhipuProviderVisionTest`：内置清单含 flash 且默认仍旗舰、视觉能力按模型判定（flash 命中、纯文本旗舰不命中、自配 `glm-4.6v` 命中）、thinking 限制断言——纯图 / 流式工具 / 图+工具复合三种场景走环境变量双 gate（有 key 才跑）。
