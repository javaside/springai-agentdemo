# v1.26.0 — 智谱联网搜索接入 + emoji 终端事故四连修复

在 [v1.25.2](v1.25.2.md) 基础上的**功能版**（minor）。核心交付物仍是终端编码智能体 **`springai-code-tui`**。

发布日期：2026-10-09。

## 新增

**① 智谱（BigModel）联网搜索——第三家搜索后端，与博查/Brave 共存**

- 新工具 `ZhipuWebSearch`（`ZhipuWebSearchTool`，自研 REST 而非官方 Java SDK——为一个 POST 引整包 SDK 会让错误转译、超时、代理与离线 stub 测试全部失控，博查先例已验证手写 RestClient 这条路可控；超时 10s/20s 不接 LlmTimeouts，搜索超 20s 就该失败）。
- 接入条件：配 `ZHIPU_API_KEY` 即启用——与智谱 LLM provider **共用同一把 key**。默认 8 条（`ZHIPU_SEARCH_COUNT`，范围 1–50），国内向长摘要源，与博查同档。
- 引擎白名单 `ZHIPU_SEARCH_ENGINE`：`search_std`（默认）/ `search_pro` / `search_pro_sogou` / `search_pro_quark`。引擎是**计费项**（四档差 5 倍：std 0.01 → sogou/quark 0.05 元/次），写错引擎可能默默选错计费档，故本地拦截而非像 freshness 那样原样透传。注意 sogou 档的 count 仅允许 10/20/30/40/50（保持默认 8 会得到 1214 参数错误），`config.env.example` 有提示。
- **`ZHIPU_SEARCH_ENABLED=0` 显式关闭**：key 与 LLM 共用意味着「配了 key」表达不了「只要模型、不要按次计费的搜索」——没充标准余额、联网搜索走 Coding Plan 套餐 MCP 的用户需要能关掉内置工具。开关只认 0（回退语义），博查/Brave 无此冲突不加。
- 配套接线：权限表登记、`RuntimeToolSet` 运行时枚举补齐；`webSearchGuide` 指引段从四态硬编码改为按三家注册状态条目拼装，指引随注册状态自动收敛。
- 文档五处同步（env 配置、工具清单、权限表、安全披露、CONTRIBUTING 冒烟门控）；安全披露顺带修正一处旧错：博查为预充值/按量计费、**无免费档**（实测 403 余额不足），计费对比只把免费档归于 Brave。
- `docs/guide/mcp.md` 补一个带鉴权的真实 MCP 示例：智谱 GLM Coding Plan 联网搜索 MCP（Streamable HTTP + Bearer header），注明**套餐 key 与平台标准 API key 不通用**、积分计费与账户余额互不相通。
- 已知取舍：200 响应形状与多域名分隔符（逗号）因账户余额不足未真机实测，解析按官方 API 参考实现；充值后跑 `ZhipuWebSearchSmokeTest`（`ZHIPU_API_KEY` + 网络双门控，余额不足显式跳过）回填。

**② `Task`/`ParallelTasks` 工具描述默认钉在当前模型（subagent 模型漂移）**

用户报告「委派 subagent 经常不在当前模型上跑」。代码默认行为本就正确（`model` 省略 → 当前激活模型），根因在**提示层**：工具描述把「subagent 自己配置的模型」当默认开头、还带模型对比诱导段；叠加外部技能文档「always specify a model / 按 tier 分档」的 REQUIRED 级指令后，守卫句失守，主模型自作主张传 `model`。修复：Model selection 段重写（第一句即「省略 model = 当前激活模型，这是预期行为而非成本陷阱」）、删除独立的模型对比诱导段（对比仅保留为「用户明确要求时才有效」的条件句）、**显式中和技能分档建议**（技能/流程文档让选分档、让 always specify model 的，不算用户要求）、`@ToolParam` 描述同步口径；4 条新测试钉住两个模板。已知留下的口子：技能文档本身未改（用户拍板本次只改工具描述）。

## 修复：粘贴 emoji 文案的终端事故四连（2026-10-09 同日四轮）

背景：用户在 Terminal.app 粘贴赛事文案（含 `9️⃣`/`8️⃣` keycap 序列，即「数字 + VS16 + U+20E3」三码点组合）后，先后出现「打字乱 → Terminal.app 崩溃 → 修后又乱/卡死/发不出/重复 → 最后整个终端应用冻住」。四轮取证定案为四个独立缺陷，全部修复：

1. **keycap/emoji 组合宽度错位（Terminal 崩溃的触发面）**：tamboui `CharWidth` 逐码点把 keycap 序列算 1 列、终端画 2 列（wcwidth 交叉验证全文 65 vs 67），输入框从序列处逐列错位，触发 Terminal.app 自身绘制缺陷（EXC_BAD_ACCESS/SIGBUS，主线程 `_platform_memmove` 越界写）。修复三层：patch 模块新增 `TerminalWidth` 序列感知宽度（keycap `[0-9#*] + FE0F? + 20E3` → 2 列，`of`/`ofPrefix`/`substringByWidth` 共用 cluster 迭代器）；shadow `Buffer.setString` 把组合按 2 列布格（base cell 含完整序列 + CONTINUATION，右边缘放不下整个序列时换空格）并把 C1 控制码（U+0080–9F）显示层换空格；code-tui 七个 UI 文件的排版/截断/光标原语统一换口径，折行不再切半组合序列。**内容一字不动**——存储与发送的原文不变。
2. **粘贴裸 CR 漏进正文**：微信 macOS 复制的多行文案行尾是纯 `\r`（会话 JSON 逐字节实证），而粘贴规范化产物只被图片/折叠两个分支消费、普通路径传的是原始 event——`\r` 行内落进输入框随正文发出。修复：普通分支同源走规范化（三路全部消费 `normalizePasteText`，`\r\n`/裸 `\r` 一律折成 `\n`）；`TextWrap` 打印层对行内控制字符（C0/DEL/C1）换空格兜底，存量会话回放等非粘贴入口也堵上。
3. **VS16 宽度反向错位**：第 1 轮曾按 wcwidth 把「⚠️ ❤️ ⏱️（文本符号 + VS16）」判 2 列，而 Terminal.app DSR 光标实测为 **1 列**（wcwidth 15.x 与 CoreText 的分歧，实测口径以终端为准）。回调为 VS16 零宽变体（宽度记 base=1，cluster 原子性保留）；keycap 2 列经同轮实机确认不变。
4. **差分渲染游标记账不同源（整个终端卡死的真根因）**：`InlineDisplay` 差分循环用 `CharWidth` 推进游标模型，而 keycap cell 的 symbol 是完整三码点序列——模型以为差 1 列、补发 `ESC[1C`，终端实际共前进 3 列，每个 keycap 让行溢出 1 列 → Terminal.app TTBuffer 越界自旋 → 整个应用无响应（jstack 抓不到，进程完全正常）。字节级实证（tmux pipe-pane 抓 app 原始字节）：修复前 `9️⃣` + `ESC[1C` + `场`，修复后紧邻。修法：三处 cell 量宽统一 `TerminalWidth`——**Buffer 布格 / InlineDisplay 游标 / 排版折行三处必须同源**（第 1 轮只修布格，把「少 1 列」变成「多 1 列」，症状相似、根因不同）。

**已知限制（定性：终端字体限制，不做代码改动）**：上述全修后，输入框里 `9️⃣场`/`8️⃣场` 存在**字形视觉重叠**——裸 `cat` 同一文本同样重叠（决定性对照），像素测量确认推进宽度就是 1 列、与 `X` 相同；根因是 SF Mono（Grass profile 在用）无 U+20E3 字形、回退方块压住后字。曾实现「显示层降级（keycap 渲染成数字+空格）」已被否决并完整 revert——改写输入框可见字符违反本项目「内容一字不动」的既定要求。彻底消除需手动换有 U+20E3 字形的终端字体（本机实测 Menlo / Monaco / Courier New / Andale Mono / PT Mono 有、SF Mono 无），换字体后终端能否正确合成 keycap 未经实测。

取证与规格材料：`docs/superpowers/` 新增三份 spec、两份 plan（emoji 宽度、CR 粘贴、智谱搜索）；事故实验会话归档至 `~/codetui-forensics`（不引用易失的 `/tmp`）。

## 验证

- **patch 模块**：`TerminalWidthTest`（keycap=2、VS16 组合=1、裸符号=1、CJK=2、ofPrefix 切点、不切半）、`BufferGraphemeCellTest`（base+continuation 布格、symbol 含三码点、右边缘换空格、C1 空格）、`InlineDisplayDiffTest`（含「keycap 不补发 ESC[1C」回归——量宽改回 CharWidth 即红）。
- **code-tui**：`SegmentedWrapTest` keycap 折行、`TextPasteCollapseTest` CR 规范化三路、`TextWrapTest` 控制字符兜底、`ZhipuWebSearchToolTest` 离线 stub 全覆盖、`AgentToolsWebSearchWiringTest` 三家注册与 `ZHIPU_SEARCH_ENABLED=0` 接线、`SubagentToolTest` 描述钉守 4 条。
- **pty 冒烟**：`keycap_smoke.py` 用两套独立 oracle 同判事故原文（keycap=2 列、纯 CR 行尾规范化）；早先「屏上 9 场」类靠 bug 蒙对的屏幕级旁证已删，keycap 行断言一律字节级。
- **用户真机终验**：重打事故原文全程可正常输入，当次会话落盘行分隔全为 `\n`（裸 CR 零残留）、keycap 序列逐字节原样（内容一字不动成立）。
- `mvn -pl springai-code-tui -am clean test`：**2376 例、0 失败、无错误、跳过 18 项**（`@EnabledIfEnvironmentVariable` 门控的真机用例）。
- `mvn -pl springai-code-tui -am package -Pdist javadoc:javadoc`：javadoc 无错误无警告。
