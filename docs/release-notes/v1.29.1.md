# v1.29.1 — 子 agent 视觉接线（委派的子 agent 现在能真正看图）

在 [v1.29.0](v1.29.0.md) 基础上的**修订版**（patch）。核心交付物仍是终端编码智能体 **`springai-code-tui`**。

发布日期：2026-10-29。

## 修复：委派出去的子 agent 看不到图片

**症状**：用 Task / ParallelTasks / 后台阶派子 agent 去看图（截图、设计稿、图表），无论
`model` 参数填什么——包括视觉白名单内的 `glm-5.3-flash`、`deepseek-flash`——子 agent 拿到的
永远是一条写着 `current model has no image input; re-reading will not show it` 的引用块，
于是只能回答「我看不到这张图」。**换任何模型都一样**，因为问题不在模型能力。

**根因是两处接线缺口**，视觉链路有一半只接在主 agent 上：

| # | 半边 | 主 agent | 子 agent（修复前） |
| --- | --- | --- | --- |
| 1 | 入站：能力快照决定引用块写 `not_in_view`（Read 一次就能看）还是 `reference_only`（看不见） | `CodingAgent.submit` 把 `provider.capabilities(modelId)` 冻结进 ToolContext | toolContext 只有 turnId/taskId，能力判定兜底成 `TEXT_ONLY` → 恒写 `reference_only` |
| 2 | 出站：把引用兑现成真 `Media` 字节 | `VisionMaterializingChatModel` 包在每 provider 主链外 | 子链只有 `RetryingChatModel`，没有视觉层 → 引用永不物化 |

`git log -S` 显示子链**从未**接过视觉层；而 `implementation-map.md` 里那句「子 agent 经
`RetryingChatModel` 桥到 stream」一直描述的是设计意图，不是实装——本版把文档一并订正。

## 修复方式

- **新增 `SubagentVision` 接缝**：把「视觉怎么接」（物化根目录、能力谓词、图像规格）留在装配点
  `AgentTools` 一处，执行器只负责调用。拆成「执行器自己 new 装饰器」会让这份知识在主/子两条链
  各写一份、必然漂移（本项目在工具容错白名单、L1 重试链序上都栽过「两处各写一份」）。
- **每次派发自带预算**：`SubagentRunner.execute` 新建一个 `VisionBudget`，与能力快照一起
  **整表复制**进该派发的 `ToolContext`；出站用同一实例兑现，工具侧
  （`MediaExternalizingCallback`）**优先读 ToolContext、回退构造注入**。
  - 这解决了三个问题：同一段 prompt 重跑时额度会累计到同一个桶（子 agent 锚点恒为 1，
    turnKey 只由锚点文本 + 下标算出）、并发/后台子 agent 之间串额度、工具侧读到「别人这次派发」
    的额度。实例隔离后额度天然按派发作用域回收，不需要释放钩子。
  - 预算**共享一个实例**看似更省，实则会让工具侧判错——它持有的是装配期那个实例，
    根本不知道「刚才这次请求属于哪个 agent」。
- **链序 `Vision(Retrying(raw))`**：Vision 在最外层，瞬时重试复用同一个已物化 Prompt，
  不会重复解码、重复扣额度；该链路走 `call` 入口，与装饰器自身 javadoc 记载的设计一致。
- **能力谓词按 provider 注入**（不是全局 `VisionModels`）、**图像规格按 provider 取**
  （`ImageProfile.forProvider`）——统一套 Anthropic 口径会让 DeepSeek 的 token 高估 3.6 倍。

## 真机验证

用 headless 模式（`-p`）在真实环境跑通四组场景：

| 场景 | 结果 |
| --- | --- |
| 主 agent 为纯文本模型（`deepseek-v4-pro`），派 `deepseek-flash` 子 agent 看左红右蓝图 | 正确报出「左半红、右半蓝，分界 x≈80」，并主动指出「文件名叫 shapes.png 但图中没有几何图形」——文件名是会诱导猜错的线索，答对说明确实读到像素 |
| 三段难猜配色（紫/橙/青纵向分段，120×150） | 按顺序全中 |
| 派纯文本模型（`deepseek-v4-pro`）子 agent 看同一张图 | 拿到 `reference_only`，明确说明没看到像素、拒绝猜色 |
| 同一回合连续两次派发完全相同的 prompt | 两次都成功（验证额度按派发隔离） |

以下为**未验证**部分，如实声明：服务端 400 拒图降级分支需要服务端主动拒图才能触发，
本次未构造该场景——该分支在生产上仍属首次启用。

## 已知边界（本版刻意未修）

- **拒绝集是实例态**：同一张被服务端 400 拒过的图，每次派发都会重新上传并再吃一次 400
  （主链是会话级记忆，子 agent 失忆）。可接受，但别指望跨派发省钱。
- **`/context` 的视觉统计不含子 agent**：一次 `ParallelTasks` 派 4 个子 agent、各 12 张图，
  这些投递在 `/context` 上不可见，而子 agent 恰恰是截图大户。
- **MCP 截图工具的「额度已尽」提示仍不准**：MCP 装饰器的预算是 `null`。本版已留好回退通路
  （工具侧优先读 ToolContext），主链补一个 key 即可修好。
- **Anthropic / 通义原生 SDK 的图片 400 不触发降级**：判据硬编码
  `com.openai.errors.BadRequestException`，故降级只对 OpenAI-SDK 系（OpenAI / DeepSeek /
  智谱 / 通义兼容端点 / opencode-go）成立。
- **主 agent 可能否定子 agent 的视觉结论**：主 agent 自己无视觉时，会提醒「Read 不解码 PNG、
  子 agent 大概率在猜」。实际图是发出去的，这条提醒是错的；系统提示尚未加「子 agent 按其
  自身模型能力读图，其报告应采信」的指引。

## 测试

新增 11 个用例（工具侧预算归属 3、能力与预算冻结 5、出站兑现 2、生产装配守卫 1）。
其中「出站兑现」做过变异验证：把 `vision.decorate(...)` 去掉后该用例立刻变红，还原后变绿——
证明它真的在测接线而不是空转。全量 2530 例 0 失败（20 例因未配环境变量跳过），
合并前后各跑一次。

## 用户可见的变化

- 委派子 agent 时，若它运行的模型支持图像输入，`Read` 图片会真正把图交给它；不支持时
  引用块照旧标注 `reference_only`，行为与 v1.29.0 一致。
- 无新增启动参数、无新增命令、无新增配置文件、无新增环境变量；不派子 agent 时行为与
  v1.29.0 完全一致。
- 计费：子 agent 的图片额度与主 agent **互不侵占**（此前若共享会互相吃额度）。
