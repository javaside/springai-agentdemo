# 设计文档：子 agent 后台模式

- 日期：2026-08-04
- 模块：`springai-code-tui`
- 类型：设计（brainstorming spec）
- 相关：[pi ⇄ code-tui 对比](../../comparisons/2026-08-04-pi-vs-code-tui.md) —— 本文实现的是其中列为「该排在 team 前面的下一步」的那一项

> **一句话**：给 `Task` / `ParallelTasks` 加 `run_in_background`——立刻返回 task id，主 agent 与用户都不再被阻塞；
> 结果经 `TaskOutput` 主动取回，或在空闲时自动起一个新回合送达。
> **现有的 `turnId` 迟到过滤、取消语义、模态队列一行不动**——后台任务走一条完全独立的通道。

---

## 1. 问题

当前 `Task` 是一次同步 `FunctionToolCallback`：函数体内直接 `SubagentRunner.run(...)`，阻塞工具线程直到子 agent 返回。`ParallelTasks` 在一次调用内 `invokeAll` 全部 join。由此产生两层阻塞：

- **模型侧**：主 agent 的工具循环停在这个 tool call 上——不能调别的工具、不能对用户说话、不能再追派任务。
- **用户侧**：输入能进队列，但要等整个回合（含全部子 agent）结束才被处理；`isBusy() || hasInFlightSubagents()` 会把新回合挡在闸门外。

README 已把它列为已知限制：「子 agent 无后台模式：`Task` 单个前台阻塞、`ParallelTasks` 一批并发前台执行（有界并发，全部 join 后返回）；暂不支持后台任务（`run_in_background` + 轮询回收）与 `/tasks` 详情面板」。

---

## 2. 已拍板的决策

| # | 决策 | 取舍 |
|---|---|---|
| D1 | **两侧阻塞都解**：主 agent 可在本回合内继续干活并主动回收，也可结束回合把任务留在后台跨回合存活 | 后台任务必须有独立于 `turnId` 的身份 |
| D2 | **完成即自动起新回合**把结果喂给主 agent | 体验最接近 Claude Code；风险集中在「自动起跑」，由 §7 的刹车承担 |
| D3 | 自动起跑条件 = **空闲 且 输入框为空** | 你正在敲字时它不抢跑；结果挂成待送达，等你这条消息发出去时一并带上（或清空输入框后它自己起） |
| D4 | 后台任务**不弹审批面板**：命中 allow 则跑，其余一律拒并写明理由 | 与 BYPASS 档「永远不停下来等人」同源；不动模态队列与迟到过滤这两处活性最敏感的代码 |
| D5 | **Esc 不碰后台任务**；`/tasks` 面板可选中终止；`/clear` 与 `/exit` 全部终止 | 「打断主 agent 的胡说八道」不该顺手杀掉跑了五分钟的后台调研 |
| D6 | `Task` 与 `ParallelTasks` **都加** `run_in_background`（默认 `false`） | 向后兼容；默认值保证现有行为零变化 |

## 3. 为什么走「独立通道」而不是「伪回合」

考虑过三条路：

**A. 独立任务注册表 + 独立事件通道**（采纳）—— 新增一张进程内任务表与一组不带 `turnId` 的事件；现有回合模型零改动。

**B. 把每个后台任务当成一个「伪回合」** —— 给每个后台任务分配 `turnId`，把 `acceptingTurnId` 从单值改成集合。省一条通道，但 `acceptingTurnId` 是**迟到过滤、streaming 归属、`cancelCurrent`、模态队列活性**四处共用的不变量，改它等于同时动这四处。而且它的缺陷模式是「静默丢事件 / 静默挂死」而非崩溃——最难测的那一类。

**C. 后台任务只记状态、不上报中间态** —— 最省事，但 ⟐ 面板看不到后台任务在跑什么，「派出去之后一片黑」。而且用户侧要靠面板终止任务，面板本来就得做，省不下多少。

**选 A 的理由**：它把新增的并发完全隔离在一条新通道上，出问题也只影响后台任务自己。B 的收益只是省一个通道，代价是拿全项目最敏感的不变量去换。

## 4. 架构

### 4.1 新增 4 个单元（全部可独立测试）

| 单元 | 职责 | 依赖 |
|---|---|---|
| `BackgroundTask` | 一个后台任务的身份 + 状态：`taskId`、`agentName`、`description`、`status`(RUNNING/DONE/FAILED/KILLED)、`startedAt`、`finishedAt`、`result`、`error`、`consumed`、`currentTool` | 无 |
| `BackgroundTaskRegistry` | 进程内任务表：登记 / 查询 / 标记完成 / 标记已消费 / 终止 / 列举。**唯一的并发真相源** | 无（纯 Java） |
| `BackgroundTaskTool` | `TaskOutput` 工具：按 taskId 取结果，支持 `block`（阻塞等待，硬超时）与非阻塞查询；取到即标记 `consumed` | Registry |
| `BackgroundNotifier` | 判定「是否该自动起回合」并合成通知文本。**纯函数**：输入 =（已完成未消费任务, 是否空闲, 输入框是否为空, 连续自动回合计数），输出 = `Optional<String>` | 无 |

**边界纪律**：`BackgroundTaskRegistry` 不认识 UI、不认识 Spring AI、不认识回合——它只是一张带状态机的表。「什么时候该自动起跑」这个最易错的判断收在 `BackgroundNotifier` 这个纯函数里，可脱离 TUI 单测。

### 4.2 改动 4 处（都是加法）

- **`SubagentRunner`**：增 `runInBackground(spec, prompt, description) → taskId`。用一个**常驻**守护线程池（`CODETUI_BACKGROUND_CONCURRENCY`，默认 4，范围 [1,32]），与现有的回合级临时池完全分开——回合取消时 `shutdownNow` 临时池碰不到它。
- **`SubagentTool`**：`SubagentCall` 与 `ParallelCall` 各加 `run_in_background` 布尔（默认 `false`）。
- **`AgentListener`**：增 3 个**不带 `turnId`** 的方法 `onBackgroundTaskStarted / Progress / Finished`，全部 `default` 空实现（回显桩与测试桩零改动）。
- **`ConversationState`**：增独立的 `backgroundTasks` 列表。**不受 `acceptingTurnId` 过滤，不被 `onTurnStarted` 清空**——这是它与现有回合级 `subtasks` 面板的分界。

## 5. 数据流

### 5.1 派发（同步，毫秒级）

```
模型 Task(run_in_background=true)
  → SubagentTool 路由 subagent_type → spec
  → SubagentRunner.runInBackground(spec, prompt, description)
      → Registry.register(taskId, RUNNING)
      → 常驻池.submit(...)                     // 不 join
  → 立刻返回："已在后台启动：task_ab12（explore · 调查登录失败）。
               用 TaskOutput 取结果，或等待完成通知。"
```

这个立即返回的文本**就是本次工具调用的结果**，所以不会留下悬空 `tool_calls`——「回合被中断后残留 assistant(tool_calls)、下一轮请求 400」那个已知坑在这条路上不存在。

### 5.2 执行（后台线程）

跑 `run(...)` 的同一套逻辑，两点不同：

1. `ToolContext` 里 `turnId` 传 `-1`、另带 `backgroundTaskId`（供权限层判定，见 §6.2）；
2. 内部工具事件只更新面板的「当前工具」，**不进 scrollback**——否则后台任务会在你与主 agent 对话的中途往对话区插自己的工具行。

### 5.3 回收：两条路，靠 `consumed` 互斥

**路径 A（模型主动，同回合内）**：`TaskOutput(task_id, block)`。命中即返回结果并标记 `consumed`。`block=true` 时阻塞等待，硬超时由**独立**的 `CODETUI_TASK_OUTPUT_TIMEOUT_SECONDS` 控制（默认 300，范围 [1, 3600]）——刻意不复用 `CODETUI_LLM_READ_TIMEOUT_SECONDS`，两者语义不同（一个是等自己的子 agent 跑完，一个是等 provider 回包），共用一个值会让调其中一个的人意外改动另一个。超时返回「仍在运行」而**不是失败**。

**路径 B（自动，跨回合）**：`CodeTuiView` 的 drain 循环每帧调一次

```
BackgroundNotifier.shouldNotify(已完成未消费, 空闲?, 输入框空?, 连续自动计数)
  → 合成通知文本 → submitHandler.submit(通知) → 该批标记 consumed
```

**两个正确性要点**：

- `consumed` 是两条路径的**互斥闸**——模型在本回合内已 `TaskOutput` 取过的任务，不会再被自动送一遍。
- 多个任务同时完成时**合并成一个回合**一次送达，不起 N 个回合。
- **判定与提交在同一个 drain 帧内完成**。drain 循环跑在渲染线程（单线程），「读输入框是否为空」与「调 `submit`」之间不会被用户按键插入，故不存在「判定时为空、提交时用户已开始打字」的竞态。

**自动起的回合就是一条普通的 user 消息**，走现有 `submit` 路径：天然进会话、天然有新 `turnId`、天然可被 Esc 取消、天然受 busy 闸门保护。**不需要伪造 tool 结果，不需要动会话事件流**——这是选 A 方案后最大的一笔省事。

通知文本形态：

```
[后台任务完成]
task_ab12 · explore · 调查登录失败 · ✓
<结果正文（已限幅，见 §7.1）>

task_cd34 · bash · 跑回归测试 · ✗
<失败原因>

以上是你先前派出的后台任务的结果，请据此继续。
```

### 5.4 进程边界

注册表是**进程内的，不落盘**。`-c` 恢复会话后，历史文本里的 `task_ab12` 已无对应任务——`TaskOutput` 对未知 id 返回「未知任务（可能来自已结束的进程）」，不报错也不空等。

> 不落盘是有意的：后台任务的价值在于「这一次会话里派出去的活」，跨进程恢复一个已经没有线程在跑的任务只会制造「它还在跑吗」的误解。

## 6. 三条冲突路径的解法

后台化真正的难点不在功能，而在它与三处既有不变量的冲突。

### 6.1 `turnId` 迟到过滤 —— `ToolEventCallback` 零改动

后台子 agent 的工具事件带的是过期的 `turnId`，`ConversationState` 会当作迟到事件丢弃。解法是把判定收在 `ConversationState`，而不是让装饰器链认识「后台」这个概念：

```
onToolStarted(turnId, taskId, ...):
    if (taskId 属于 backgroundTasks)  →  更新该任务 currentTool，return
    ...原有的 turnId 迟到过滤照旧
```

一句前置判断，换来 `ToolEventCallback` 一行不动。

### 6.2 权限 —— 只在「会产生 ASK 的档位」需要特殊处理

`PermissionCallback` 已经从 `ToolContext` 取 `turnId` 与 `taskId`（不读 ThreadLocal，因为它在 `ToolEventCallback` 外层），所以判定点是现成的：`backgroundTaskId` 非空时改判。

**关键澄清：BYPASS 档不存在这个矛盾。** 其判定顺序是「deny 规则 → BYPASS 放行 → 后面全跳过」，**根本不产生 ASK**。按档位展开：

| 档位 | 后台任务的额外处理 |
|---|---|
| **默认** | 文件写 / 非白名单命令 / 网络 / 未登记与 MCP 的 ASK → **DENY** |
| **自动接受编辑** | 工作区内的写与文件系统命令本就 ALLOW → **照常放行**；区外与网络的 ASK → DENY |
| **计划模式** | 写与命令本就是 DENY → **与前台无差别**；网络的 ASK → DENY |
| **跳过权限检查（BYPASS）** | **零特殊处理，与前台完全一致** |

deny 规则与 allow 规则在所有档位下行为不变。

**内置底线在后台档给 DENY 而不是 ASK**，与计划模式是**同一条推理**：这一档承诺了「不停下来等人」，就不能把一个本该被拦的操作变成唯一能当场批准的口子。README 已为计划模式写过这段论证，此处沿用。

**被拒时的返回文本必须写全三件事**：被拒的是哪个调用、为什么（后台任务不弹审批面板）、以及**按当前档位给出的正确下一步**：

- 默认档 → 「改用 `run_in_background=false` 的前台 Task 重试，或先为该操作添加 allow 规则」
- 自动接受编辑档 → 同上，并说明工作区内的写本可自动放行（提示该目标在区外）
- 计划模式 → 「这一档本就不动手，请把发现报告回主 agent」

> 不按档位分支就会出现「模型被拒了但不知道怎么办」，它会对同一个操作反复重试直到耗光回合——这与计划模式当初必须给专属提示是同一个教训。

**后台任务能真干活的三条路**（写进用户文档）：① 事先写窄 allow 规则；② 切到「自动接受编辑」档（工作区内编辑自动放行，区外与网络仍挡住，是实用的中间档）；③ `--dangerously-skip-permissions` 启动。

> **BYPASS 与后台任务在设计意图上互补**：README 给 BYPASS 的理由是「永远不会停下来等人，这正是它在半无人值守下能用的原因」，而后台任务正是半无人值守的典型形态。

### 6.3 busy 闸门 —— `inFlight` 必须拆成两个计数

现在 `hasInFlightSubagents()` 只要有任何在飞子 agent 就挡住新回合。后台任务若计入，**后台化等于没做**。

- `foregroundInFlight` —— 闸门用，语义不变（被取消的回合可能仍有前台子 agent 在跑，不能并发写同一会话）
- `backgroundInFlight` —— 只供面板显示与退出清理

后台任务本身不写会话（独立上下文，结果只经通知文本进会话），自动回合走 `submit` 受闸门保护，故拆开后无并发写风险。

### 6.4 生命周期

| 事件 | 后台任务 |
|---|---|
| `Esc` 取消回合 | **不受影响** |
| `/tasks` 面板 `k` | 终止选中的运行中任务（`shutdownNow` + 标记 KILLED），先确认 |
| `/clear` | 全部终止并清空注册表（新会话不该有旧会话的任务在跑） |
| `/exit` | 有界终止，硬限 2s，照抄 MCP 子进程清理的「不卡退出优先」取舍 |

## 7. 三个刹车（本设计的安全边界）

### 7.1 通知文本限幅

后台任务结果经通知进 user 消息 = **直接进会话 = 永久占上下文**。一个话痨的 explore 子 agent 能一次性打掉一大块。

- 完整结果落盘 `.codetui/artifacts/task-<id>.txt`
- 通知里只放前 **4000 字符** + 一行 `[结果已截断，完整 N 字符见 <路径>，可用 Read 取回]`

> 这是「工具输出限幅」这条通用防线的一个特例。必须先做掉自己这一份：现在至少还有人看着，**后台任务是没人看着的**。

### 7.2 自动回合失控刹车

自动起的回合可能又派后台任务 → 又自动起回合 → 无限循环烧钱，而且是在你不在电脑前的时候。

- 记**连续自动回合计数**：中间没有任何用户输入的情况下，连续自动起跑超过 **3** 次即停止自动
- 改为状态栏提示 `⏱ N 个后台任务结果待处理 · 回车交给模型`
- **任何一次真实用户输入都重置计数**

> 这个阀门不是可选项——D2「完成即自动起新回合」的全部风险都集中在这里。

### 7.3 任务数上限

| 项 | 值 | 超出时 |
|---|---|---|
| 在飞并发 | `CODETUI_BACKGROUND_CONCURRENCY`，默认 4 | 排队 |
| 等待队列 | 16 | `Task` 直接返回「后台队列已满，请改用前台 Task 或等待」——对模型而言拒绝比静默排队更清晰 |
| 注册表总容量 | 64 | 按「最旧的已完成任务」淘汰；**运行中的永不淘汰** |

> **`ParallelTasks` 部分入队失败时不整批拒绝**：逐条入队，入得进的照常启动，入不进的那几条在返回的结构化汇总里单独标注「未启动：后台队列已满」。这与它既有的失败隔离语义一致——一条不成不该拖垮另外几条。

### 7.4 其余边界

| 情况 | 处理 |
|---|---|
| 后台任务抛异常 | 标记 FAILED，`SubagentRunner.describe()` 摊平 cause 链作结果（复用现有实现），**不影响主 agent 的任何回合** |
| `TaskOutput(block=true)` 超时 | 返回「仍在运行」，**不失败**——超时不等于任务死了 |
| 未知 taskId | 「未知任务（可能来自已结束的进程）」，不报错不空等 |
| 自动回合的 `submit` 抛异常 | 记 WARN，任务**保持未消费**，下一帧再试。一次失败不能把结果丢掉 |
| 递归派发 | **不存在**：`SubagentRunner` 收到的是 `decoratedList`，`Task`/`ParallelTasks` 只加进主 agent 的 `toolsWithTask`，子 agent 拿不到 Task 工具 |

## 8. UI

### 8.1 ⏱ 后台任务面板（新增，与 ⟐ 面板分开）

生命周期不同：⟐ 面板由 `onTurnStarted` 清空（回合级），后台任务跨回合存活。混在一个面板里，清空语义迟早写错。

**零任务时不出现**，不占行。注意 TamboUI 的 scope 每帧 eager 求值——面板方法首行必须判空。

```
⏱ 后台任务 (2 运行 · 1 完成)
  ▶ ab12 explore  调查登录失败          1m42s  Grep
  ▶ cd34 bash     跑回归测试            0m18s  Bash
  ✓ ef56 plan     设计缓存层            2m03s  待送达
```

### 8.2 状态栏

空闲且有后台任务在跑时，在权限模式标识**之后**追加 `⏱ N 个后台任务 · /tasks`。

不放行首——那个位置属于权限模式：状态行接近终端宽度、尾部先被截断，而「现在会不会问你」比「有几个后台任务」更不该被截掉。

### 8.3 scrollback 行

每条都必须是**单物理行**（`println` 会把多行塌成一行截断）：

```
⏱ 后台任务已启动  ab12 · explore · 调查登录失败
✓ 后台任务完成    ab12 · 调查登录失败 (1m42s)
✗ 后台任务失败    cd34 · 跑回归测试 (0m18s) · <摊平的一行原因>
```

### 8.4 `/tasks` 面板

| 键 | 行为 |
|---|---|
| ↑↓ | 选择 |
| Enter | 展开 / 收起结果全文 |
| `k` | 终止选中的运行中任务（先确认，照 `/permissions` 的 `d` 删除确认做法） |
| Esc | 关闭 |

与 `/permissions` 一致**任何时候可开**（不像 `/mcp` 要求空闲——终止后台任务不会撞在飞的工具调用）。

底部常驻一行提示，解决「结果卡在待送达」这个必然会遇到的困惑：

```
ⓘ 已完成的任务会在你清空输入框后自动交给模型处理
```

### 8.5 一个实现时的坑

自动起回合的通知文本是**多行**的，它走 `submit → onUserMessage` 这条路。项目已在「一个 OutputLine = 一个物理行」上踩过坑（ASSISTANT 行必须单行、`-c` 回放须按 `\n` 逐行拆）。**用户消息这条路径必须同样按 `\n` 拆**，否则通知会被塌成一行截断——而这恰好是最需要看清楚的内容。

## 9. 测试策略

测试命令一律带 `-pl springai-code-tui`（整仓 `-Dtest` 会被空模块打挂）。

### 9.1 纯单元（无 Spring、无 TUI）—— 主战场

- **`BackgroundTaskRegistry`**：状态机迁移、`consumed` 幂等、容量淘汰只淘汰已完成的（运行中永不淘汰）、并发登记/完成不丢
- **`BackgroundNotifier`**：三条件真值表（空闲? × 输入框空? × 有未消费?）、多任务合并成一条通知、连续自动回合刹车计数与用户输入重置
- **通知限幅**：截断点、路径行、不需截断时不加尾注

### 9.2 接缝层

- **`SubagentTool`**：`run_in_background=true` 立刻返回 taskId 文本；`=false` 走原路径（回归）
- **`PermissionCallback`**：**4 档 × 6 种判定的权限矩阵**在 background 标记下的结果 —— 本次最该钉死的一张表，它是安全语义
- **`ConversationState`**：后台 taskId 的工具事件不受 `turnId` 过滤、不进 `pending`；前台事件逐条回归
- **`SubagentRunner`**：计数拆分后 `hasInFlightSubagents()` 只看前台

### 9.3 渲染层（`Frame.forTesting` + 反射 `markAsRenderThread` 渲进离屏 Buffer）

⏱ 面板零任务时不出现、状态符号、耗时格式；状态栏后缀不挤掉行首的权限模式标识。

### 9.4 pty + pyte 实机

派任务 → 面板出现 → 完成 → 自动起回合 → **通知多行正确换行**（§8.5 那条只有实机能验）；`/tasks` 开关与 `k` 终止确认流。

注意 `wait_for` 会命中陈旧 scrollback，断言「当前状态」不能只靠子串。

### 9.5 变异测试

逐个隔离，且输入须满足除目标外的**全部**前置条件：

| 变异 | 应当失败的断言 |
|---|---|
| 去掉 `consumed` 标记 | 结果被送两遍（`TaskOutput` 取过之后又自动送） |
| 去掉自动回合刹车 | 连续自动起跑不停 |
| 去掉 `inFlight` 拆分 | 后台任务挡住新回合（后台化失效） |
| 权限矩阵里 background 的 ASK 改回 ASK | 后台任务弹出审批面板 |
| 去掉通知限幅 | 长结果整段进会话 |

> 第三条尤其要防假绿：测「后台任务不挡新回合」时，输入必须构造成**只有后台任务在飞、没有任何前台子 agent**，否则会被前台那条闸门顺手挡住而看不出变异。

真实 LLM 调用走 env 门控的冒烟测试，默认跳过。

## 10. 范围外（本期不做）

| 项 | 理由 |
|---|---|
| 后台任务**跨进程持久化** | 恢复一个已无线程在跑的任务只会制造「它还在跑吗」的误解（§5.4） |
| 后台任务**弹审批面板** | D4 已定；要做得先解决「空闲时弹审批」的交互与模态队列活性，成本远超收益 |
| **共享任务列表 / 任务依赖 / 认领** | 那是 agent teams 的范畴，见对比文档；后台模式是它的前置，不是它 |
| **子 agent 之间横向消息** | 同上 |
| **git worktree 隔离** | 独立有价值（并发写同一棵树的隐患），但与本期正交，单独立项 |
| 后台任务的**成本单列显示** | 依赖尚未实现的成本核算（对比文档 P0-7） |

## 11. 验收标准

1. `Task(run_in_background=true)` 在 **1 秒内**返回 task id 文本，主 agent 可在同一回合内继续调用其他工具。
2. 派出后台任务后**立刻**结束回合，用户可**立即**提交下一条消息（`hasInFlightSubagents()` 不被后台任务拉高）。
3. 后台任务完成且「空闲 + 输入框为空」时，自动起一个新回合，通知文本**多行正确显示**、模型能据此继续。
4. 模型在同一回合内用 `TaskOutput` 取过的结果，**不会**再被自动送一遍。
5. 后台任务撞到需审批的调用时**不弹面板**，返回文本按当前档位给出正确的下一步；BYPASS 档下行为与前台完全一致。
6. `Esc` 取消回合后，后台任务**仍在跑**；`/tasks` 面板可见并可 `k` 终止；`/clear` 与 `/exit` 全部终止。
7. 连续 3 次自动回合后**停止自动**，改为状态栏提示。
8. 超过 4000 字符的结果被限幅，完整内容落 `.codetui/artifacts/task-<id>.txt` 且可 `Read` 取回。
9. `run_in_background` 缺省或为 `false` 时，行为与改动前**逐条一致**（回归测试钉死）。
