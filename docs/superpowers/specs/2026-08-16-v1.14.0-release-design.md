# v1.14.0 发布设计

**日期**：2026-08-16
**基线**：`v1.13.0`
**范围**：本地发布准备，不推送远端、不创建 GitHub Release

## 目标

将 `v1.13.0` 之后已合入 `main` 的流式稳定性与状态栏可读性改进发布为 `springai-agentdemo` v1.14.0 功能版。核心交付物仍为终端编码智能体 `springai-code-tui` 的两个自包含运行包。

发布主题为：**流式调用不再无限卡住，缓存状态更易扫读**。

## 相较 v1.13.0 的发布内容

### LLM 流式空闲超时保护

全部六家 provider 的流式模型调用统一增加首包及相邻数据块之间的空闲超时。默认 300 秒无新数据时主动结束当前流，通过现有错误路径恢复 UI 的可提交状态，避免状态栏永久停在思考或运行中。

超时沿用 `CODETUI_LLM_READ_TIMEOUT_SECONDS` 配置，合法范围仍为 10–3600 秒。上游已经返回的明确超时错误保留原始信息，不被本地兜底文案覆盖；超时发生前已收到的 usage 仍在错误传播前提交，缓存统计不丢失。

### 忙碌态缓存命中率

`THINKING` 与 `RUNNING_TOOL` 状态行继续显示当前会话累计 `缓存命中 N%`。忙碌态不重复显示上下文占比，以控制行宽；工具摘要会为缓存命中率、权限模式标签和取消提示让出空间。

### 状态栏优先级与高亮

空闲状态栏在窄终端中按“模型及动态状态 > Enter 主操作 > 次要帮助组”保留内容。`/model`、`Esc`、`Ctrl+C` 空间不足时整组隐藏，非默认权限模式标签计入宽度预算，避免动态数据再次被挤出 80 列终端。

`IDLE`、`THINKING`、`RUNNING_TOOL` 中的缓存命中率仅将完整百分比值 `N%` 渲染为冷薄荷色加粗；标签、分隔符、上下文百分比和 `/context` 报告保持原样。

## 版本与文档

- 根 POM及六个子模块 POM 的项目/父版本统一从 `1.13.0` 更新为 `1.14.0`，共七处。
- 新增 `docs/release-notes/v1.14.0.md`，只描述 `v1.13.0..HEAD` 的实际用户行为变化，不把规格和实施计划列为产品功能。
- 在 `CHANGELOG.md` 顶部增加 v1.14.0 功能版索引。
- 运行环境仍为 JDK 17+，支持 macOS、Linux、Windows；不新增第三方依赖。

## 构建与产物

执行：

```bash
mvn -pl springai-code-tui -am clean package -Pdist
```

构建必须成功且测试零失败、零错误，并生成：

- `springai-code-tui/target/springai-code-tui-1.14.0-dist.tar.gz`
- `springai-code-tui/target/springai-code-tui-1.14.0-dist.zip`

两份归档都必须包含启动脚本、主 jar、运行依赖、配置示例、README、指南、LICENSE 和 NOTICE。归档内主 jar 的 manifest 必须包含 `Implementation-Version: 1.14.0`。

## 校验和流程

1. 先完成版本号、CHANGELOG 和发布说明初稿，SHA 区暂写固定文本 `构建完成后写入最终校验值`；该文本在发布提交前必须完全移除。
2. 执行完整 dist 构建并检查测试、文件名、归档内容和 manifest。
3. 计算两个归档的 SHA-256。
4. 将最终测试统计与 SHA-256 回填到仓库中的 `docs/release-notes/v1.14.0.md`。
5. 回填后不再重建归档，避免归档包含发布说明时产生无法自指固定的哈希循环。仓库和未来 GitHub Release 正文中的 SHA 以步骤 3 的最终产物为准。
6. 用 `shasum -a 256 -c` 对发布说明中的两项校验值做一次实际验证。

## 提交与标签

静态检查、构建、归档和 SHA 验证全部通过后：

- 创建发布准备提交：`release: v1.14.0 发布准备`；提交尾注包含 `Co-Authored-By: CodeTui <noreply@codetui.dev>`。
- 在该提交上创建 annotated tag `v1.14.0`，tag message 为 `springai-agentdemo v1.14.0`。
- 不 push `main`，不 push tag，不创建 GitHub Release，不上传产物。

## 失败处理

任何版本一致性检查、测试、构建、归档内容、manifest、SHA 或静态检查失败，都停止后续步骤。在所有验证完成前不创建发布提交和 tag；若 tag 名已存在则停止，不覆盖已有 tag。
