# TodoWrite「建了清单不更新」根因分析

状态：v7（2026-10-08）。v6 的区分变量（「进入 SDD 循环前会话内是否已有 TodoWrite 节奏」）
经**全语料 322 会话**同口径复核后**证伪**——按该变量二分，装载前 0 次组配对率 0.28、
≥1 次组 0.41，组内各自从 0.00 跨到 0.57/1.00，不构成 v6 主张的「完美分离」。
结论重排为**两层**：确定的 harness 缺陷（清单对模型单向、零反馈）+ 统计性的触发器
（完成时刻的「记账槽位」被占）。取证可复跑：[dev/session-forensics/todo_staleness.py](../../../dev/session-forensics/todo_staleness.py)。

关联实现：[2026-10-07-todo-stale-reminder-design.md](2026-10-07-todo-stale-reminder-design.md)。
v6 结论留档见[附 B](#附-bv6-结论存档已证伪)。

## TL;DR（v7）

「建了清单不更新」不是单一原因，而是**一个确定缺陷被若干统计性触发器反复触发**：

- **确定层（harness 缺陷，唯一必须由环境修的一层）**：清单对模型是**只写、零反馈**的。
  TodoWrite 的返回值是一次性静态文案，面板是 UI 层、模型看不见，harness 没有任何机制把
  过期清单送回上下文。于是**任何一次漏更新都不可逆**——它不产生任何可观察后果，也没有
  任何东西会把状态纠正回来。这一层解释了「为什么漏一次就漏到底」。
- **统计层（触发器）**：「把一个工作单元记为完成」这个时刻，模型手里有一个**记账槽位**，
  但里面可以放的东西不止 TodoWrite。实测这一槽位被三类内容占据：
  ① SDD 的台账行（具体到格式模板、且不点名 TodoWrite）；② 委派本身——完成发生在子 agent
  里，控制器看到的是一次 `Task` 返回，而工具描述里的 "After completing a task" 是写给
  「自己完成任务」的语义；③ 任何更长、更具体的流程文本。
  度量结果：控制器做出完成标记时顺手更新清单的比例，非 SDD 会话 **0.63**，SDD 会话 **0.37**；
  但「冻结到底」并非 SDD 专属——冻结跨度 ≥50 且有完成标记的会话里，非 SDD **20 个**、SDD 仅 3 个。
- **不可解释的会话内差异（诚实标注）**：配对率在 0.00~1.00 之间连续分布，两类分区内部都
  有极好与极差的会话。n=14 的 SDD 样本**切不出决定成败的会话级变量**；v6 提出的「节奏」
  不是它（见证据 3）。

因此修复方向：确定层由 `TodoStaleReminder`（已交付）兜住；统计层把纪律**绑到「记账/提交」
这个具体事件**上，而不是绑到「规划阶段热身」。

### 方法与指标

脚本：[dev/session-forensics/todo_staleness.py](../../../dev/session-forensics/todo_staleness.py)（只读会话 JSON，不改任何东西）。

```bash

```

语料：本机 15 个会话目录、**322 个可解析会话**，其中**建过清单的 184 个**、**SDD 会话 14 个**。
（前几版分析只扫了 3 个目录 / 224 个会话，样本更大也更偏——本次是首次跨项目全量。）

三个指标（定义以脚本 docstring 为准，改口径必须同步改文档）：

- **实质工具调用**：全部 toolCall 剔除 `BashOutput` / `TaskOutput`。这两个是轮询等待
  （一次 `mvn` 全量测试能刷出几十次），不剔除会把冻结跨度虚报成几十。
- **冻结跨度**：清单处于「有未完成项」状态期间，连续实质工具调用的最大值。
- **配对率**：控制器做出**完成标记**（`git commit`，或写入 ledger/progress 台账）时，
  此刻清单仍有未完成项 → 该事件或紧接着的下一个工具调用事件里出现 TodoWrite 即算配对。

### 口径边界（解读这些数字时必须一并说明）

- 分区只有「本会话出现过 `Skill(subagent-driven-development)`」一条；SDD 会话的规划期
  也被计入冻结统计，因此该分区对 SDD 是**保守**的（会低估其冻结程度、高估其配对率）。
- 配对率度量的是**「做出完成标记那一刻」的顺手更新**，不统计中途的提前勾选；
  而 `git commit` 也可能属于清单之外的新工作（见证据 2 的 bf1cc7 末段）。故它是
  「顺手程度」的带噪估计，靠 505 个标记的大样本摊平，不用于单会话判定。
- 冻结跨度不表示「模型错了」：清单合法停在 in_progress 也会计入。它的用途是横向比较
  分区与找出极端样本，再逐个抽查形态（证据 2 即如此做）。
- 会话是真实工作记录，不是对照实验：任务形态、模型、配置都在变，**只支持相关性判断**。
- 完成标记的判定有两处刻意的严格化，都会**轻微低估**标记总数：台账只在「写入重定向/写回
  语义与 ledger/progress 路径同现」时计入（`cat >> …progress.md`、python 内联脚本
  `s += …` 写回两种真实形态都覆盖；`cat progress.md` 读回不计），`git commit` 必须出现在
  行首或命令分隔符之后（`bash -c "git commit …"` 这类包在引号里的会漏计）。同时排除
  分析脚本自身命令（本仓库 `dev/session-forensics/` 的命令行里就含这些字面量），
  否则每次跑分析都在污染自己的样本。
- 数字是 2026-10-08 一次运行的快照（脚本输出可复现）；会话目录是活数据，重跑可能因
  新会话/新提交小幅漂移。

## 已证实的因果链（v7）

### 层 1（确定缺陷）：清单对模型单向，零反馈

- 面板在 UI 层，模型看不见；TodoWrite 的返回是一次性静态文案，此后永不再现；
- harness 无任何机制把过期清单重新送进模型上下文；
- 写不写 TodoWrite 对任务推进、审查结果、台账内容**没有任何可观察差异**。
- 结果：**一次漏更新即永久化**。层 2 的触发器只是决定「哪一次会漏」，层 1 决定「漏了就到底」。
- 这一层是「一次修复即可消除」的，`TodoStaleReminder` 正对准它。

### 层 2（统计触发器）：完成时刻的记账槽位被占

- 完成时刻模型手里有一个「记账槽位」。工具描述教的动作是「完成任务→更新清单」；
  但实际会话里，占住这个槽位的东西更具体、离得更近：
  - SDD 台账行：有格式模板、由 skill 在流程图上反复点名（`Append completion to ledger,
    mark todo complete`），却**不点 TodoWrite 的名字**；
  - 委派：完成发生在子 agent 内，控制器看到的是一次 `Task` 返回，「自己完成任务」的语义不成立；
  - 长流程文本普遍比一行工具纪律更具体。
- 度量即证据 1：非 SDD 0.63 vs SDD 0.37。**这不是「SDD 的错」**，而是「具体流程动作挤掉通用工具纪律」
  这一机制在 SDD 上表现得最充分。
- 同一机制也解释了 v6 观察到的「台账独占后成为照抄模板」——它其实是层 1 的表现，不是独立环节。

### 层 3（不可解释）：会话内随机性

- 配对率在两类分区内部都从 0 跨到 1；同一个模型、同一个项目、同一天可以一好一坏。
- 诚实结论：**现有数据不足以找出会话级决定变量**。这层不需要解释，需要的是兜底（层 1 的修复）。

## 责任归属

- **层 1（确定）**：harness 缺陷，必须修，且是唯一能保证「次数不限、路径不限」的一层。
- **层 2（统计）**：修法是把纪律绑到具体事件（记账/提交）上，提高顺手的概率；不指望它兜住全部。
- **skill 文本**：不需要、也不应该提 TodoWrite——`b65902`（0 次热身、配对 0.57）证明
  同一份 skill 可与良好维护共存；把纪律写进工具纪律层/系统提示词，与任何流程文本解耦。
- **第三方 skill 一字不动**：不可控（上游重同步即覆盖）。2026-10-08 已把本地修订恢复原样。

## 待验证假说（v7 修订）

**「把更新纪律绑定到『记账/提交』事件（而非『规划阶段热身』），能提高非 SDD 场景的顺手更新率
并缩短 SDD 场景的冻结跨度。」**

- 依据：非 SDD 会话里存在天然的「commit → TodoWrite」绑定（0.63，且 `ece0c4` 类会话近乎
  每次都带）；SDD 里这个绑定被台账动作挤掉。
- 可证伪实验：在系统提示词里写「每次提交/记账后先更新清单」，跑同型 SDD 与同型非 SDD 会话各若干，
  比较配对率与冻结跨度。若无改善 → 该假说推翻，说明槽位竞争不受文本干预，只能依赖运行时注入。
- 与 v6 的差别：v6 要求「规划阶段起就用 TodoWrite 热身」，其目标变量已被证伪；
  本假说绑定的是**事件**，可用配对率直接度量成败。

## 附 B：v6 结论存档（已证伪）

> **v6 TL;DR（原文，2026-10-08）**：成败由「进入执行循环前，TodoWrite 是否已是本会话的
> 工作节奏」决定：A/B 在规划阶段持续使用（9/11 次），进入 SDD 后顺着自身惯性逐任务更新；
> F 规划全程 0 次、唯一一次是与台账 Write 捆绑的开场动作，首个完成点没有节奏可顺、
> 被 skill 规定的具体台账动作轻取，此后自我锁定，环境零反馈永不翻盘。
> 因果链：**种子缺失（进入循环前无使用节奏）→ 台账轻取首个完成点 → 自我锁定 → 零反馈固化。**

留档理由：该结论方向（环境放大与固化）部分正确，但把「同一行为的更早一次测量」当成了原因，
并依赖一份未记录会话路径、事后无法重建的对照。v7 用可复跑脚本替代了不可复核的人工对照——
这是本次修订最重要的方法学教训：**凡是写进文档的「实测事实」，都必须留下任何人能重跑的命令与输入。**
