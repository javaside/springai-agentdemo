# TodoWrite「建了清单不更新」根因分析

状态：v6 终版（2026-10-08。v5 的「随机性」推进为可操作的种子变量：**进入 SDD 循环前
会话内是否已有 TodoWrite 使用节奏**——F 规划阶段 0 次 vs A 9 次 / B 11 次，完美分离成败）。
关联实现：[2026-10-07-todo-stale-reminder-design.md](2026-10-07-todo-stale-reminder-design.md)。

## TL;DR（v6 终版）

**成败由「进入执行循环前，TodoWrite 是否已是本会话的工作节奏」决定**：A/B 在规划阶段
持续使用（9/11 次），进入 SDD 后顺着自身惯性逐任务更新；F 规划全程 0 次、唯一一次是与
台账 Write 捆绑的开场动作，首个完成点没有节奏可顺、被 skill 规定的具体台账动作轻取，
此后自我锁定，环境零反馈永不翻盘（xibaojun 五场 SDD 光谱 30/13/4/20/1 与此一致）。

因果链：**种子缺失（进入循环前无使用节奏）→ 台账轻取首个完成点 → 自我锁定 → 零反馈固化。**

对最初问题「模型原因还是提示词原因」的最终回答：**种子层是概率性的（同 skill 同模型，
F 的规划期抽到 0 次），但成败被环境放大与固化——修复因此全在 harness 侧**：
① 系统提示词纪律段把「热身」变成硬要求（种子）；② Task 返回事件对齐提醒（放大）；
③ 计数版提醒器（固化，已合入）——三者把概率行为变成确定性维护。

## 已证实的因果链（三层）

### 层 1（种子）：进入执行循环前，会话内没有 TodoWrite 使用节奏

- 实测：F 规划阶段 TodoWrite 调用 **0 次**（ev0~120，含完整 plan 编写与审核）；
  对照 A **9 次**（ev7~74）、B **11 次**（ev29~329）——0 对 9/11，三会话完美分离成败。
- F 唯一一次调用（ev125）与台账 Write 捆绑在同一事件，是 SDD 开场 setup 动作，未形成节奏。

### 层 2（放大）：首个完成点被 skill 规定的台账动作轻取，随后自我锁定

- skill 的完成动作具体（带格式模板）；有节奏的 A/B 顺着惯性顺手带上 TodoWrite
  （Task 返回→更新台账→TodoWrite 三段式 72.7%/66.7%），无节奏的 F 没有可顺的惯性
  （0/8），台账独占后成为后续每一轮的照抄模板。
- **注意：skill 文本本身不是病因**——A/B 用同一份 skill（同样 0 次提及 TodoWrite）
  维护完美。「流程不含 TodoWrite」的说法（v3 结论）已被对照实验推翻。

### 层 3（固化）：零反馈 + 自我模式强化

- 面板是 UI 层，模型看不见；TodoWrite 返回是一次性静态文案（#126 后永不再现）；
- harness 无任何机制把过期清单重新送进模型上下文；
- 写不写 TodoWrite 对任务推进、审查结果、台账内容**没有任何可观察差异**；
- 对照会话里由用户催办（「请先回顾你的 todo 列表」×4）人肉充当了反馈回路；F 无催办。

**责任归属**：种子层的抽签是概率性的，但成败由环境放大与固化——修复全在 harness 侧。
skill 不需要、也不应该提 TodoWrite（A/B 证明同一份 skill 可与完美维护共存）；
维护清单是 **agent 的常驻纪律**，由系统提示词（纪律层）与提醒器（强制层）保障，
与任何流程文本解耦。

## 待验证假说（修复方向的理论依据，非病因结论）

**「工具描述中的行为规则对非 Claude 系模型约束力弱于系统提示词，故把更新纪律写进
系统提示词可在动作竞争中胜出。」**

- 支持理由：业界双通道惯例（我们自己的系统提示词里本就有 TodoWrite 指引行）；
  Claude 系模型被训练成把工具描述当行为契约，别家无此保证。
- **不能作为病因**：见排查表 #7——`tools` 放置在成败两组间相同。
- 可证伪实验：把纪律段写进系统提示词，重跑同型 SDD 会话（同模型、同 skill），
  观察更新行为是否恢复。恢复 → 假说成立，系统提示词修法有效；不恢复 → 假说推翻，
  只能依赖运行时注入。

## 修复方案

| 修法 | 针对层 | 状态 |
|---|---|---|
| `TodoStaleReminder` 运行时注入（计数版，默认 8 次触发；事件对齐版：Task/ParallelTasks 返回即触发） | 层 2 零反馈（事件版兼补层 1：在动作选择现场递指令） | 计数版**已交付**（main）；事件版待做 |
| 系统提示词增加任务清单纪律段（含委派语义：subagent 返回过审 = 完成，先更新再继续） | 层 1 动作槽（依据上述**待验证假说**，建议先跑对照实验） | 待做 |

第三方 skill（subagent-driven-development）**一字不动**：不可控（上游重同步即覆盖）、
与工具无绑定关系、修订收益有限；曾有本地修订，2026-10-08 已恢复原样。

## 附：工具信息的放置原则（工程惯例建议）

| 信息性质 | 例子 | 放哪 |
|---|---|---|
| 接口文档：是什么、怎么调、参数/返回约束 | 入参 schema、"Pass the FULL list every call" | `tools` 字段（随 schema 走，唯一合法位置） |
| 行为纪律：什么事件必须用、用完的义务 | 「每任务完成先更新再继续」 | 系统提示词（所有模型都保证当指令读的通道） |
| 现场强制：此刻必须做 | 「subagent 刚返回、清单未动 → 现在更新」 | 运行时注入（工具结果尾部） |
