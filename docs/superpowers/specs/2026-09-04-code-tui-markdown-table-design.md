# code-tui Markdown 表格渲染 设计

日期：2026-09-04
状态：初稿 v1（brainstorming 已确认样式与时机，待 writing-plans 展开）
参考实现：Claude Code 的表格渲染（表头加粗 + 一条分隔线，不画竖线）

## 0. 摘要

code-tui 的 markdown 渲染器**没有表格分支**，表格行原样打印。因此模型吐出的表格在终端里
是否对齐，完全取决于模型有没有把每个格子补到等宽——而它做不到：GFM 不要求竖线对齐，
且模型按**字符数**补齐、终端按**显示宽度**排版（CJK 占 2 列）。结果是用户实报的
「表格显示就乱了」。

本设计给渲染器补上**表格块渲染**：攒够整块后按显示宽度算列宽、重排成轻量表
（表头加粗 + 一条 `─` 分隔线 + 空格对齐，不画竖线），超宽时削列 + 格内折行、不丢字。
核心约束是 scrollback **只能追加、印出去改不了**，所以列宽必须在打印前算完，
表格块只能先缓冲、块结束才输出——本设计的主要复杂度都在「什么时候算块结束」。

## 1. 背景：现状与实测证据

### 1.1 现状：整个模块没有表格处理

`MarkdownRenderer`（`springai-code-tui/src/main/java/io/github/javaside/springai/codetui/ui/MarkdownRenderer.java`）
只有五个分支：代码围栏、标题、引用、列表、内联样式。表格行掉到最后的
`renderInline()`（同文件 `:145`）被原样打印。全模块 main + test 内 grep
`startsWith("|")` / `isTable` / 「表格」均零命中——不是实现有 bug，是这个功能不存在。

生产渲染路径：`ASSISTANT` 逻辑行 → `ScrollbackPrinter.assistantCursor`（`:266`）
或流式路径 `streamingLinesCursor`（`:271`）→ 每条逻辑行 `md.renderFinalized` →
`SegmentedWrap.styled(..., innerWidth())` 按显示宽度折行 → 每段前置 2 空格缩进 →
一段一个 `println`（一个 `println` = 一个物理行）。折行本身按显示宽度算、中文按 2 列，
是**正确**的（`TextWrap` / `SegmentedWrap`）。

### 1.2 实测（探针走真实渲染路径）

用一张 4 列中英混排表喂 `assistantCursor`，记录落到 scrollback 的物理行：

| 终端宽 | 产出 | 各行显示宽度（含 2 空格缩进） | 结果 |
|--------|------|------------------------------|------|
| 120 列 | 4 行 | 33 / 33 / 88 / 86 | 表头与分隔行 33 列、数据行 88 列，竖线上下不可能对齐 |
| 80 列 | 6 行 | 33 / 33 / 80 / 10 / 80 / 8 | 数据行按显示宽度硬折，切在格子中间：`… 取值 neve` + 续行 `r/auto \|` |

（源行显示宽度 31 / 31 / 86 / 84，缩进后各 +2。）

用户截图的旁证：纯 ASCII 表（模型恰好补齐了）完全对齐、box-drawing 表（宽度自洽）
正常，只有中英混排 + 长数据行的表乱——三者共同证明渲染器只是照抄，宽度计算无 bug。

### 1.3 目标 / 非目标

**目标**

- 模型吐出的 markdown 表格在终端里列对齐，中英混排也对齐（按显示宽度，CJK 2 列）
- 超过终端宽度时不切在格子中间、不丢字
- 流式、`-c` 回放、一次性三条路径产出一致
- 不破坏既有纪律：一个 `println` = 一个物理行；drain 分批预算不被单块输出独占

**非目标**

- 无外侧竖线的 GFM 写法（`a | b`）——原样输出，不识别（见 3.3 的边界理由）
- 单元格内 `<br>` / 块级内容（列表、代码块）
- resize 后重新排版（见第 4 节已知局限）
- 表格之外的 markdown 行为改动

## 2. 候选方案与取舍

| 方案 | 做法 | 取舍 | 裁决 |
|------|------|------|------|
| A. 攒整块再输出 | 表头+分隔行到位就开始缓冲，块结束一次性排好输出 | 列宽按真实内容算，最优且不丢字；代价是表格「憋」到整块收完才出现（实测通常 < 1s），且需要四条 flush 兜底路径 | **采纳** |
| B. 边流边排，列宽拍死 | 表头到位就把终端宽按列平分，后续行流到就按该宽度填、格内折行 | 不憋、不需要 flush 钩子；但列宽与内容无关——`String`/`auto` 这种短列白占 20+ 列，长列反被挤得频繁折行 | 否 |
| C. 只修超宽 | 不做对齐，只让折行表格感知（不在格子中间切） | 改动最小、零架构风险；但 1.2 里「表头 31 列 / 数据行 86 列」的主要症状没治 | 否 |

样式在 A 之下另有三选（轻量表 / box-drawing 网格 / 对齐的管线表），解析与列宽计算
完全共用，只是输出长相不同。选**轻量表**：4 列时只多吃 6 列宽（另两种多吃 13 列），
窄终端 + 中文内容下最不容易触发削列，且与本项目「仿 Claude Code」的既有风格一致。

## 3. 详细设计

### 3.1 输出规格（轻量表）

- **列宽** = 该列所有格子（含表头）显示宽度的最大值，中文按 2 列
- **列间** 固定 2 空格；**不画竖线**
- **表头**加粗（复用 `MarkdownRenderer.BOLD`）；表头下一条 `─` 分隔线通到全表宽，暗色（复用 `DIM`）
- **对齐**：分隔行的 `:---` / `:--:` / `---:` 认左 / 中 / 右；无冒号默认左
- **内联样式**：格子内的 `**粗**` / `` `代码` `` 照常渲染，但列宽按**去掉标记后的可见宽度**算
- **整表**与正文同样带 2 空格缩进（`ScrollbackPrinter.INDENT`），每个物理行独立 `println`

**超宽处理**：设可用宽度 `inner = 终端宽 − 2`（缩进）。需要的总宽 =
`Σ列宽 + 2 × (列数 − 1)`。超过 `inner` 时：

1. 从最宽的列开始削，反复削最宽者直到总宽装下（水位法，避免把一列削成 0）
2. 每列有最小宽度 **4 列**（容得下 2 个 CJK 字符或 4 个 ASCII 字符）
3. 削完后格子内容**按空格换行**排到多行；单个词比列还宽才硬切（按显示宽度，不切半个宽字符）
4. 连最小宽度都装不下（列数太多）→ **整块退回原样输出**，即当前行为，诚实降级

80 列终端下，1.2 那张表排完是这样（总宽 22+2+6+2+6+2+38 = 78）：

```
  参数                    类型    默认值  说明
  ────────────────────────────────────────────────────────────────────────────
  codetui.syncOutput      String  auto    控制是否使用终端同步输出扩展，取值
                                          never/auto/always，写错会退回默认值
  codetui.hardwareCursor  String  auto    控制硬件光标可见性，Apple Terminal 的
                                          IME 路径需要 always 才正常
```

### 3.2 `MarkdownTable`（新增，纯函数无状态）

`ui` 包新增一个类，只做解析 + 排版，不碰 IO 与状态，可独立单测：

- `static boolean looksLikeRow(String line)`——`stripLeading` 后以 `|` 开头
- `static boolean isSeparator(String line)`——单元格全由 `-` / `:` / 空格组成且至少一个 `-`
- `static List<Alignment> alignments(String separatorLine)`
- `static List<List<Span>> render(List<String> block, int width)`——块原文 → 排好的若干行 spans

解析细节：

- 按**未转义**的 `|` 切分；`\|` 还原成字面 `|` 且不作分隔符
- 首尾的空单元格（行首行尾竖线产生的）丢弃
- 单元格数与表头不一致按 GFM：多的丢、少的补空
- 每个格子先过 `MarkdownRenderer` 的内联解析拿 spans，列宽用 **spans 内容拼起来的显示宽度**
  （不是原文宽度），否则 `**粗**` 的 4 个星号会把列撑歪

### 3.3 `MarkdownRenderer` 块状态机

在既有渲染器上加三个成员方法（`renderFinalized` / `renderPreview` 保持原样，
当非表格行的原语，现有 `MarkdownRendererTest` 不动）：

- `List<List<Span>> feed(String line, int width)`——吃一条逻辑行，吐 0..N 条渲染好的行
- `List<List<Span>> flush(int width)`——把缓冲里的表格块排出来；空缓冲返回空列表（幂等）
- `boolean hasBuffered()`——缓冲里是否压着表格块。`ScrollbackPrinter` 以
  `hasBufferedTable()` 转发给视图，视图不直接碰渲染器

一次性入口 `assistant(String)` / `streamingLine(String)`（当前只有测试在用）同样改走
feed + 收尾 flush，保证与游标路径同源。

状态机放在 `MarkdownRenderer` 里而不是外面，理由是**围栏内的 `|` 不能当表格**，
而围栏开合状态只有它有。表格块状态与围栏状态同属「块上下文」，放一起才不会撕裂。
宽度作为**参数**传入（不存字段），排版本身仍是无状态的。

状态与转移（`feed` 的语义）：

| 当前状态 | 输入行 | 动作 | 返回 |
|----------|--------|------|------|
| 空闲 | 围栏内 / 非 `\|` 开头 | 走 `renderFinalized` | 该行 1 条 |
| 空闲 | `\|` 开头 | 押住当候选表头 | 空 |
| 候选 | 是分隔行 | 进块（表头 + 分隔行入缓冲） | 空 |
| 候选 | 不是分隔行 | 候选行按普通行渲染，再渲染当前行 | 2 条（顺序不变） |
| 块内 | `\|` 开头 | 入缓冲 | 空 |
| 块内 | 其它（含空行） | 排出整块，再渲染当前行 | N+1 条 |

**一行 lookahead 的代价**：正文里行首带竖线的句子会被延迟一行显示。只影响行首是 `|`
的行，且由 3.4 的兜底 flush 收口，不会永久卡住。这也是「只认行首竖线」的取舍来源——
若放宽到 GFM 的 `a | b`，任何含竖线的正文句子（如 `ps aux | grep java` 的说明文字）
都会被押住一行，误伤面大得多。

### 3.4 flush 触发点（本设计的主要风险面）

scrollback 只能追加，四条都必须有，漏一条就是**内容消失或顺序错乱**：

1. **块内来了非表格行**（含空行）→ 先吐表格，再吐这行。（3.3 状态机内部，天然满足）
2. **非 markdown 正文行入队前**：`CodeTuiView.enqueueOutputLine`（`:517`）的
   `USER` / `TOOL_START` / `default` 三个分支前面插一个 flush cursor。必须**走队列**
   而不是直接打——直接打会让表格跑到工具行后面去，输出顺序反了。
3. **回合结束**：视图在每批输出段（`CodeTuiView.java:875` 取流式完整行那一带）观察到
   「输出队列空 + pending 空 + 回合已 IDLE」且 `printer.hasBufferedTable()` → 入队 flush。
   `onTurnComplete`（`ConversationState.java:980`）、`onError`（`:996`）、Esc 取消三条路径
   最终都落到状态转 IDLE，故共用这一条。**以表格结尾的回复全靠它**——漏了就是表格永远不出现，
   直到用户再发一句话（`onUserMessage` 的回合间留白才把它顶出来）。
4. **`/clear`**（`CodeTuiView.java:2161` 一带）→ 丢缓冲，与 `outputQueue.clear()` 同语义。

### 3.5 缓冲上限与降级

缓冲超过 **200 行**或 **64 KB** → 把已攒的**原样**吐出，并把该块标记为降级，
剩余行流式原样输出直到块结束。防病态输入（模型吐几千行表格）把内存和「憋」的时长做没边。

排出时仍是一次 `next()` 一个物理行（`MdLineCursor` 挂一个小的待吐队列，
`hasNext()` 要把它算进去），所以 drain 的分批预算不受影响——与 `toolStartCursor`
在工厂调用时展开整个 diff、之后逐行惰性产出是同一个模式。

### 3.6 流式期间的预览行

`renderPreview(tail)` 显示的是「在建残行」，属于活动区不是 scrollback。表格缓冲期间它继续
原样显示当前半截行。观感是：缓冲期间屏幕上只有当前这一行在动、上面不累积，整块收完后
表格一次性落下。这是「攒整块」的必然表现，已确认接受。

## 4. 已知局限（诚实声明）

- **resize 后不重排**：留底原文（`PhysicalLine.raw`）是排好的整行 Text，resize 重放只会
  按新宽度**重折**、不会重新算列宽。窗口缩窄后滚回去看历史表格，列会错位。今天的行为
  也是错位（本来就没对齐），不算回归；重排需要把「块」而不是「行」作为留底单位，属另一件事。
- **无外侧竖线的表**原样输出，见 1.3 非目标。
- 缓冲期间遇到进程崩溃，缓冲里的行不会落到 scrollback（会话记录不受影响，落盘走的是另一条路）。

## 5. 测试策略

TDD，先红后绿。分四层加一个实机冒烟：

1. **`MarkdownTableTest`（纯单测）**：列宽 / 三种对齐冒号 / CJK 双宽 / `\|` 转义 /
   单元格数不齐（多的丢少的补）/ 内联标记不计入宽度 / 超宽削列 + 格内按空格折行 /
   单词超列宽硬切不切半个宽字符 / 列数太多退回原样
2. **`MarkdownRendererTableTest`**：3.3 状态转移表逐行钉住——块起止、候选行不是表格时
   两行顺序不变、围栏内 `|` 不识别、`flush` 空缓冲幂等、降级上限触发后剩余行原样
3. **`ScrollbackPrinterTest` 增补**：走真实 `assistantCursor` 与 `streamingLinesCursor`
   （**不要用一次性的 `assistant(String)`**——它不按 `\n` 拆，多行文本会变成一条带内嵌
   换行的 Line，产出与生产路径不同；这个坑在本设计的探针阶段已踩过一次）。
   120 列与 80 列各断言：每个物理行显示宽 ≤ 终端宽、各行列起点的显示偏移一致、
   内容拼回去一个字不丢
4. **视图级**：表格缓冲期间插一条 `TOOL_START` → 断言表格先出、工具行后出；
   回合结束 / `onError` / Esc 取消三条路径都排空缓冲；`/clear` 丢缓冲
5. **pty 冒烟**（项目规矩：改渲染必实机验证）：造一个含表格的会话文件走 `-c` 回放，
   在真实屏幕上断言各行列起点一致、没有裂行。复用 `resize_smoke.py` 的 `PtySession`
   骨架（记得 `TIOCSWINSZ` + `TERM=xterm-256color`，否则读到全空白）

验证命令按模块作用域跑：`mvn test -pl springai-code-tui -Dtest=...`（整仓 `-Dtest` 会被
空模块打挂）。

## 6. 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| flush 触发点漏一条 | 表格永不显示 / 顺序错乱 | 3.4 四条各有测试；视图级测试覆盖顺序 |
| 一行 lookahead 押住正文行 | 行首带竖线的句子晚一行出现 | 只认行首竖线，缩小面；兜底 flush 收口 |
| 列宽算错（内联标记 / CJK） | 又是一版错位 | 宽度一律走 spans 拼接后的显示宽度；单测钉双宽与标记 |
| 大表格独占一批输出 | UI 卡顿 | 排出仍逐行惰性；200 行 / 64 KB 上限降级 |

## 7. 实施切分（供 writing-plans 展开）

1. `MarkdownTable`（解析 + 列宽 + 削列 + 格内折行）+ 单测——纯函数，可独立完成
2. `MarkdownRenderer.feed/flush/hasBuffered` 状态机 + 单测
3. `MdLineCursor` 消费 0..N 行（待吐队列 + `hasNext()` 修正）+ `tableFlushCursor()`
   + `ScrollbackPrinter` 增补测试
4. 视图接线：`enqueueOutputLine` 前置 flush、每批空闲兜底 flush、`/clear` 丢缓冲 + 视图级测试
5. pty 冒烟 + 全量回归（`mvn test -pl springai-code-tui`）
