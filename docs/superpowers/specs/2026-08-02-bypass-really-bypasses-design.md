# 设计文档：BYPASS 真正跳过全部检查（+ 留痕）

- 日期：2026-08-02
- 模块：`springai-code-tui`
- 类型：设计（brainstorming spec）
- 性质：**行为变更**（改的是 v1.6.0 已发布的权限语义）
- 前置：[2026-07-31 权限模式设计](2026-07-31-permission-mode-design.md)、[2026-08-02 匹配漏洞设计](2026-08-02-permission-matching-holes-design.md)

> **一句话**：一个写着 `--dangerously-skip-permissions` 的开关，打开之后还在弹窗，那它就是在骗人。

---

## 1. 问题

用户在 TUI 里跑半无人值守的自动化开发（丢一个大任务给 agent 然后人离开），发现**即使开了 `--dangerously-skip-permissions` 仍会卡在等人应答**。

### 1.1 为什么会卡

决策链共 6 步，而 BYPASS 只在**第 6 步**才放行。排在它前面的三步在 BYPASS 下照常执行：

| 步 | 内容 | BYPASS 下 | 会不会卡人 |
|---|---|---|---|
| 1 | deny 规则 | 硬拒 | 不卡（直接拒，回合继续） |
| 2 | **内置底线** | **强制 ASK** | **卡** |
| 4 | **ask 规则** | **ASK** | **卡** |
| 6 | 模式默认 | 放行 ← BYPASS 在这里 | — |

第 2 步在代码里是 `askOnly(...)`，注释写着「刻意 askOnly：本步排在 allow 规则之前，加任何 allow 规则都消不掉这次询问，给建议就是骗人」。

### 1.2 卡住之后没有出口

`PermissionCallback` 阻塞在容量 1 的一次性队列上，**`take()` 无超时**。解除阻塞只有两条路：UI 应答，或回合被 dispose。人不在场就是死等。

（非 TUI 场景另有一个默认 listener 会立即 DENY，所以无头调用不会挂——但那不是本文要解决的场景。）

### 1.3 原设计错在哪

「护栏不是牢笼，人确认了就该能做」这条原则本身没错，但它**默认了总有人在场**。人不在场时，护栏变成死锁。

更糟的是它的**二阶效应**：一个名字里带 `dangerously` 的开关，用户已经承担了全部心理成本去打开它，结果发现它是假的。这会教用户「这个项目的开关不可信」——比多弹几次窗伤害大得多。

---

## 2. 决定

### 2.1 BYPASS 判定从第 6 步提到第 1 步之后

```
1. deny 规则        → 硬拒（保留）
   ★ BYPASS         → 直接放行，以下全部跳过
2. 内置底线          ← BYPASS 下不再执行
3. （预留插槽）
4. ask 规则          ← BYPASS 下不再执行
5. allow 规则
6. 模式默认
```

### 2.2 为什么 deny 规则保留

三者的**来源不同**：

| | 谁定的 |
|---|---|
| 内置底线 | 写死在代码里的清单——**本项目的意见** |
| deny / ask 规则 | 用户写在 `permissions.json` 里的——**用户的明令** |

BYPASS 的字面意思是「跳过**审批**」，不等于「无视我立过的禁令」。而且 `<项目根>/.codetui/permissions.json` 是**仓库带来**的——clone 别人的仓库时，那里的 deny 规则本来就是保护你的。

**ask 规则则不同**：它的语义是「每次都问我」，而 BYPASS 的前提是「不问」。二者直接矛盾，此时按 BYPASS 走（自动放行）是唯一自洽的解释。

### 2.3 关键性质：BYPASS 下永远不阻塞

deny 命中时**直接拒绝并告知模型**，不弹窗、不等人，回合继续。所以开了 BYPASS 就不存在「卡住等人」这件事——这是本次变更要保证的**核心不变量**，须有测试钉住。

### 2.4 PLAN 模式不受影响

第 2 步里针对 `PLAN` 的特例（危险操作在 PLAN 下降级为 DENY 而非 ASK）仍在原处。PLAN 与 BYPASS 是两档，互不相干。

## 3. 留痕：放弃拦截，不放弃告知

内置底线的价值有两半：**拦住你**，和**让你知道发生了什么**。本次放弃前一半，但**不该连后一半一起丢**——尤其用户明确说了「人会回来看」。

### 3.1 即时行

BYPASS 下命中内置底线时，往 scrollback 打一行（不阻塞、不询问）：

```
⚠ BYPASS 放行：Write .git/hooks/pre-commit（通常需要确认）
```

### 3.2 回合末汇总

一个回合里若有过这类放行，回合结束时汇总一次：

```
⚠ 本回合 BYPASS 放行了 3 个通常需要确认的操作：
   · Write .git/hooks/pre-commit
   · Read ~/.aws/credentials
   · Bash rm -rf $BUILD_DIR
```

**为什么两个都要**：即时行保证「正在发生时屏幕上有」，汇总保证「回来时不必翻几百行 scrollback」。半无人值守场景两者都必要。

### 3.3 接缝：一个回调就够

`AgentListener` 已有现成先例 `onRuleRecorded(long turnId, boolean ok, String message)`——权限层向 UI 报「规则记下了没」的默认空实现。留痕照同一形状加一个：

```java
/** BYPASS 下放行了一个通常需要确认的操作。默认空实现，便于回显桩/测试桩省略。 */
default void onGuardrailBypassed(long turnId, String what) { }
```

**汇总不另加回调**：视图按 `turnId` 累积，在已有的 `onTurnComplete(turnId)` 里 flush 并清空。少一个接缝、少一处要保持同步的状态。

### 3.4 不做的

- **不写日志文件**——本项目日志目录的接线另有问题（曾出现 logback 配置期 WARN 撕裂 TUI），不在本次范围。
- **不做「事后追认」交互**——那等于把审批挪到事后，复杂度不值。

### 4.1 已发布的发版说明不改

v1.6.0 的说明是**已经发出去的承诺**，偷偷改掉等于篡改历史。正确做法：留着原文，在**下一版发版说明**里明确写一条行为变更：

> **`--dangerously-skip-permissions` 的语义变了**：v1.6.0 里它保留了内置底线（仍会弹窗），本版起**真正跳过全部检查**，只有你自己写的 deny 规则仍然生效。原因：那个开关在无人值守场景下会卡死，而一个名字带 `dangerously` 的开关不该是假的。

`CHANGELOG.md` 是纯发版索引表，同样等发版时再进。

## 5. 测试

### 5.1 必须能失败的（每条配逐个隔离的变异）

| 断言 | 变异 |
|---|---|
| BYPASS 下命中内置底线 → **ALLOW**（不是 ASK） | 把 BYPASS 判定挪回第 6 步 → 必红 |
| BYPASS 下命中 ask 规则 → **ALLOW** | 同上 → 必红 |
| BYPASS 下命中 deny 规则 → **DENY** | 去掉第 1 步 → 必红 |
| **BYPASS 下不存在任何 ASK 结果**（核心不变量） | 上述任一变异 → 必红 |
| PLAN 下危险操作仍 DENY | 误删 PLAN 特例 → 必红 |
| DEFAULT / ACCEPT_EDITS 下内置底线**仍然** ASK | 把跳过写成无条件 → 必红 |

最后一条尤其重要：**这次改的是 BYPASS 一档，另外三档的行为必须一个字不变**。

### 5.2 留痕的测试

- 命中内置底线且模式为 BYPASS → 产生一条留痕记录；其它模式下不产生
- 回合末汇总只列本回合的、且去重

### 5.3 pty 实机

`permission_smoke.py` 里凡断言「BYPASS 下仍弹窗」的用例须反转。**留痕行是否真出现在屏幕上**只能实机验（本项目 TUI 渲染栽过多次）。

## 6. 风险与取舍（如实记录）

- **这是安全性的净下降**，换来的是「开关不再说谎」和「无人值守可用」。用户在明确知情下选择了它。
- **提示注入后果放大**：模型被网页说服去 `rm -rf ~` 时，BYPASS 下不再有最后一道询问。留痕能让你**事后**发现，不能阻止。
- **留痕只进 scrollback**：`/clear` 或滚出屏幕就没了，不落盘。
- **deny 规则成为唯一防线**：想在无人值守下保留某些禁令，必须自己写进 `permissions.json`。README 要明说这一点，否则用户不知道还有这条路。
